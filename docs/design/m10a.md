# M10a — Conversaciones de notificación confiables

**Versión objetivo:** `v0.10.0`. **Estado:** diseño y contrato de entrada.

## 1. Propósito y frontera

M10a permite que un operador autorizado continúe una sesión bloqueada desde
Slack o Telegram. No convierte esos servicios en una consola de administración:
el único efecto remoto admitido es entregar una respuesta de texto a una sesión
ya existente, viva y bloqueada. `ntfy` y webhook conservan su contrato saliente;
la suscripción de respuesta ntfy se adapta al mismo contrato interno.

Un repositorio no puede habilitar canales, fijar tokens, destinos, allowlists ni
tiempos de expiración. Toda esta configuración vive sólo en
`~/.corral/config.toml` o en las variables de entorno del operador; las reglas
de rechazo de configuración de repositorio se amplían con cada clave nueva.

## 2. Contrato común

Cada backend transforma su mensaje autenticado en una `IncomingMessage`:

| Campo | Significado | Requisito |
|---|---|---|
| `backend` | `ntfy`, `slack` o `telegram` | constante controlada por código |
| `message_id` | identidad opaca del proveedor | no vacía, estable por reintento |
| `sender_id` | identidad autenticada del emisor | no vacía; se compara con allowlist |
| `chat_id` | conversación/destino de entrada | no vacía; se compara con allowlist |
| `received_at` | instante observado por corral | reloj inyectado, no timestamp del proveedor |
| `body` | texto de la respuesta | máximo `answer.MaxBytes` |

`Conversation.Accept` es la única puerta de entrada. Primero valida backend,
allowlist, tamaño y sintaxis `<sesión> <respuesta>`; luego rechaza duplicados o
mensajes vencidos; sólo después confirma que la sesión está bloqueada y llama
a `InputWriter.WriteInput`. La respuesta se codifica mediante `answer.Encode`,
nunca se interpreta como shell. La aceptación escribe `session.answered` con
`via`, `message_id` y una huella de identidad redactada; no persiste el texto,
el token ni identificadores de terceros en claro.

## 3. Deduplicación, ack y expiración

La identidad de deduplicación es `(backend, message_id)`, persistida de forma
durable antes de escribir a la PTY. Así un reinicio después de recibir un
webhook no puede inyectar la misma respuesta dos veces. El registro contiene
sólo backend, id opaco con hash y `accepted_at`; tiene TTL configurable y una
operación de poda auditable. Un `message_id` repetido responde con un ack
idempotente y no reintenta la escritura.

El ack es una abstracción del backend, no un privilegio: Slack recibe el ack
HTTP dentro de su plazo, Telegram confirma el `update_id` sólo después de que
corral registró el resultado, y ntfy no necesita respuesta remota. Fallar un
ack puede causar reintento del proveedor; la deduplicación lo vuelve seguro.

Las respuestas vencen después de `notify.conversation.reply_ttl` desde su
recepción. No se acepta una hora aportada por Slack/Telegram para decidir la
vigencia. La expiración impide que un webhook retenido continúe una sesión días
después; el rechazo se registra localmente sin reflejar contenido sensible.

## 4. Configuración y mínimos privilegios

```toml
[notify.conversation]
reply_ttl = "10m"
dedupe_ttl = "24h"

[notify.slack]
enabled = true
bot_token = "…"              # secreto, sólo chat:write e im:history
signing_secret = "…"         # secreto, valida cada request
allowed_users = ["U123"]
allowed_chats = ["D456"]

[notify.telegram]
enabled = true
bot_token = "…"              # secreto, sólo getUpdates/sendMessage
allowed_users = ["123456"]
allowed_chats = ["-100123"]
```

Slack valida firma, timestamp y nonce antes de decodificar el payload; rechaza
una desviación mayor a cinco minutos. Telegram utiliza long-poll saliente por
default (sin puerto entrante); su `update_id` es la identidad de deduplicación.
Los backends no aceptan una URL o certificado elegidos por un repositorio, no
leen variables no incluidas en el snapshot del daemon y usan clientes HTTP con
`Proxy: nil`.

## 5. Redacción y observabilidad

El dispatcher redacta el texto de notificación antes de cualquier egress. La
entrada conserva la política inversa: registra sólo metadatos mínimos y la
longitud de la respuesta, nunca el cuerpo. Cada decisión produce un evento
auditable `notify.reply_{accepted,rejected,duplicate,expired}` con backend y
causa estable. Tokens, firmas, cuerpos y headers no entran a eventos, logs,
errores CLI ni métricas.

## 6. Verificación

- pruebas de tabla para allowlists, backend desconocido, TTL, límite de bytes,
  sesión inexistente/no bloqueada y redacción de auditoría;
- prueba de reinicio: un mensaje aceptado antes del reinicio es duplicado
  después, sin segunda escritura en PTY;
- servidores fake para firma Slack, replay, ack tardío, updates Telegram fuera
  de orden y reintentos de ambos proveedores;
- pruebas negativas de configuración de repositorio para cada secreto,
  allowlist y TTL;
- red real exclusivamente en un workflow manual/opt-in con secretos del
  operador, nunca en CI de pull request.

**Cierre de M10a:** una sesión bloqueada genera aviso, una identidad admitida
responde y la sesión continúa en Slack y Telegram; una identidad o replay no
admitido no llega a la PTY ni expone secretos.
