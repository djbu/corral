# M8 — Cierre seguro del workflow de review

**Versión objetivo:** `v0.8.0`. **Estado:** contrato congelado antes del código.
**Alcance:** pasos 55–59 de `docs/roadmap/POST_M6.md`.

## 1. Resultado observable

Una tarea ejecutada en un worktree conserva su estado de ejecución actual y
adquiere un estado de revisión independiente. El operador puede inspeccionar
un preflight sin escritura y, mediante una segunda acción explícita, liberar
el resultado con una estrategia elegida o descartarlo de forma recuperable.
Ningún cambio entra en la rama destino sólo por terminar un DAG.

## 2. Estados y persistencia

`tasks.status` continúa significando únicamente ejecución. M8 no reinterpreta
filas antiguas ni hace que el orchestrator vuelva a programarlas.

La columna `tasks.base_commit` conserva la base exacta del worktree. Una tabla
`task_reviews`, relacionada uno-a-uno con `tasks`, conserva:

- `status`: `pending_review`, `released` o `discarded`;
- último `strategy`, `target_ref`, `target_before` y `result_commit`;
- `recovery_ref`, cuando existe;
- timestamps de creación y última mutación.

El orchestrator crea la fila y captura `base_commit` inmediatamente después
de crear el worktree. Una tarea sólo llega a `pending_review` cuando termina
`succeeded`; los fallos y cancelaciones siguen inspeccionables pero no se
pueden liberar. Las tareas históricas no reciben un `base_commit` inventado:
se muestran como legacy y su preflight rechaza una mutación insegura.

## 3. Identidad y ownership

Antes de cualquier mutación se resuelven y comparan:

- repo canónico persistido;
- worktree registrado por `git worktree list --porcelain`;
- rama registrada y su ref exacta;
- `base_commit`, HEAD de la rama de tarea y HEAD de la rama destino;
- limpieza del worktree de tarea y del worktree destino.

La rama de tarea `corral/task/<dag-id>/<name>-a<N>` debe conservar el nombre
creado por corral y apuntar al HEAD observado. El namespace del DAG evita
colisiones entre ejecuciones que reutilizan un nombre. El target debe ser una
rama local, estar actualmente checkout en
el repo principal y coincidir con el `expected_target_head` enviado por el
operador. Un cambio después del preflight produce conflicto; nunca se aplica
sobre una identidad distinta.

## 4. Preflight sin escritura

`GET /v1/tasks/{id}/review/preflight?strategy=...&target=...` ejecuta sólo
lecturas de filesystem y Git. Devuelve identidades completas, estado sucio,
commits por aplicar, divergencia y una lista estable de blockers/warnings.
El preflight nunca crea refs, índices, worktrees ni archivos temporales.

Estrategias:

- `merge`: merge explícito, sin resolución automática de conflictos;
- `cherry-pick`: commits `base_commit..task_head` en orden;
- `branch`: conservar la rama sin modificar la rama destino.

`merge` y `cherry-pick` exigen target limpio y sin operación Git en curso. El
preflight usa `git merge-tree` para detectar conflictos previsibles. El gate
definitivo vuelve a comprobar todas las identidades bajo un lock por repo.

## 5. Release

`POST /v1/tasks/{id}/review/release` requiere estrategia, target y
`expected_target_head` (salvo estrategia `branch`). El handler no confía en
paths proporcionados por el cliente.

La operación se serializa por repo. Si Git falla, corral ejecuta el abort
correspondiente (`merge --abort` o `cherry-pick --abort`) y no cambia el estado
persistido. Un abort es rollback mecánico, no resolución de conflictos.
Sólo después de éxito se marca `released` y se registra el commit resultante.
La estrategia `branch` no toca el target y conserva worktree y rama.

No se hace push y no se borra la rama de tarea en M8.

## 6. Descarte recuperable

`POST /v1/tasks/{id}/review/discard` requiere el `expected_task_head` exacto.
Por defecto rechaza un worktree sucio. Antes de retirarlo crea una ref
`refs/corral/recovery/<task-id>/<timestamp>` apuntando al HEAD comprobado.
Después retira el worktree; la rama de tarea se conserva, por lo que corral
nunca borra commits cuya autoría no pueda demostrar.

`force=true` permite retirar un worktree sucio sólo tras repetir la identidad
exacta de repo, rama, path y commit en la petición. Los cambios no committeados
no son recuperables y esa pérdida se declara en el preflight y en el evento.
No existe un `--force` implícito.

## 7. API, scopes y auditoría

Las rutas de lectura respetan el scope DAG existente. Las mutaciones de review
por TCP requieren token `admin`; un token `session` recibe `403`. El socket
Unix conserva su frontera local de permisos.

Cada intento crea un evento daemon-scoped sin secretos ni diff completo:

- `review.release_succeeded` / `review.release_failed`;
- `review.discard_succeeded` / `review.discard_failed`.

Los datos incluyen task, repo canónico, estrategia, refs y commits exactos.
El cambio de estado y el evento de éxito se escriben en una sola transacción.

## 8. CLI y dashboard

- `corral review release <task> --strategy merge|cherry-pick|branch
  [--target <branch>] [--expect <sha>]`;
- `corral review discard <task> --expect <sha> [--force]`;
- `corral review <dag> --diff` conserva la inspección existente y añade
  review status, base y preflight;
- dashboard muestra diff/preflight, identidades completas y confirmaciones.

Los botones nunca eligen estrategia, target ni SHA silenciosamente. Durante
una petición quedan deshabilitados y el resultado se recarga desde el API.

## 9. Pruebas y salida

- unit tests de parser/preflight y transiciones persistidas;
- fixtures Git reales para camino feliz, dirty, branch adelantada, base
  divergente, conflicto, carrera de HEAD y rollback;
- tests HTTP de scope, cuerpos estrictos, idempotencia y errores estables;
- E2E de navegador opt-in sobre TLS + bearer + SSE;
- dogfood en repos temporales: release, conflicto, crash/reintento y discard
  recuperable;
- migración desde schema 6, backup/restore y smoke de upgrade desde `v0.7.0`.

M8 se cierra sólo cuando un DAG real completa
create→work→review→release, otro termina en discard recuperable, ningún camino
de fallo modifica el target y el tag anotado `v0.8.0` pasa todos los gates.
