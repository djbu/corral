# corral M2 design — hooks-driven state engine (the moat)

> Intended location: `docs/design/m2.md`. Read `RUNBOOK.md` §2/§5.3/§7/§10, `docs/design/m1.md` (§2 seams, §7.4 pinned settings, §11 step-0 discipline), and `docs/spike-notes.md` first. This document resolves every structural choice for M2; the implementer should not need to invent architecture.

> **Provisional-until-step-0 notice.** Every concrete Claude Code hook shape in this document (§2's `hooks{}` nesting, §3's per-event payload field lists, §5's Notification semantics) is written from recall of Claude Code hook behavior and is **provisional**. Step 0 (§12) captures real fixtures from CLI 2.1.224 into `testdata/hooks/2.1.224/`. Those fixtures — not this document — are the authority; they also become the fuzz corpus (§11) and fakeclaude's fidelity source (§9). Where a step-0 result would change the design, the alternative branch is named inline. Do not build §3–§5 before step 0 lands.

---

## 0. What M2 is, in one paragraph

M1 gave corral a daemon that owns PTYs and a `state.Engine` seam whose only implementation derives `agent_state` from process status. M2 fills that seam: corral pins a real `hooks{}` block into each session's `--settings` file, every hook invokes `corral hook-relay`, the relay POSTs the raw payload over the unix socket authenticated by a per-session secret, and a real `state.Engine` turns that stream into `working / blocked(reason) / idle`. On the transition **into** blocked, a notifier fires. `corral answer` writes the reply back into the PTY. Nothing scrapes terminal text, ever — that is the entire point of the milestone.

**Scope boundaries decided here, up front:**

- `internal/claude/streamjson/` is **M4, not M2.** Decisive argument: M2's only session mode is interactive PTY (M1 §7.3 — no `-p`, no `--output-format`). A PTY-hosted `claude` emits a TUI, not stream-json. The parser is literally unreachable in M2. It arrives with the headless runner that produces its input.
- **API errors are out of reach in M2.** RUNBOOK §2 lists "API error" as a `Blocked(reason)` variant. No hook event fires on an API error; the only signal is TUI text or stream-json. M2 ships three of the four reason kinds honestly rather than heuristically inferring the fourth. `kind: "api_error"` is reserved in the schema and produced by M4.
- **Auto-answering (deciding permissions on the agent's behalf) is M4.** The relay's response seam exists (§2.5) and is exercised by a test, but the daemon always answers "no decision" in M2.

## 2. Hook wiring

### 2.1 The pinned `hooks{}` block

M1 writes `settings.json` containing exactly `{"hooks": {}}`. M2 replaces that constant with a generated block. The shape (**provisional, confirm in step 0 V13/V20**):

```json
{
  "hooks": {
    "SessionStart":     [{ "hooks": [{"type":"command","command":"<RELAY> --event SessionStart","timeout":5}] }],
    "UserPromptSubmit": [{ "hooks": [{"type":"command","command":"<RELAY> --event UserPromptSubmit","timeout":5}] }],
    "PreToolUse":       [{ "matcher":"*", "hooks":[{"type":"command","command":"<RELAY> --event PreToolUse","timeout":5}] }],
    "PostToolUse":      [{ "matcher":"*", "hooks":[{"type":"command","command":"<RELAY> --event PostToolUse","timeout":5}] }],
    "Notification":     [{ "hooks": [{"type":"command","command":"<RELAY> --event Notification","timeout":5}] }],
    "Stop":             [{ "hooks": [{"type":"command","command":"<RELAY> --event Stop","timeout":5}] }],
    "SubagentStop":     [{ "hooks": [{"type":"command","command":"<RELAY> --event SubagentStop","timeout":5}] }],
    "PreCompact":       [{ "hooks": [{"type":"command","command":"<RELAY> --event PreCompact","timeout":5}] }],
    "SessionEnd":       [{ "hooks": [{"type":"command","command":"<RELAY> --event SessionEnd","timeout":5}] }]
  }
}
```

`<RELAY>` is `<absolute path to the running corral binary> hook-relay`, resolved once at daemon startup via `os.Executable()` + `filepath.EvalSymlinks`, shell-quoted. Never `corral` bare: the child's `PATH` may not contain it, and PATH-resolution of a security-relevant helper is an injection surface.

`--event <Name>` is redundant with the payload's `hook_event_name` **on purpose**: it is the cross-check that catches a payload-shape change in a future CLI version (§3.3 mismatch rule), and it makes the relay usable when the payload fails to decode at all.

`WebSearch`/`WebFetch`/tool-name-specific matchers are not used. One matcher-all registration per tool event; classification happens in the daemon where it is testable, not in a settings file that cannot be unit-tested.

**`timeout: 5`** is a defensive per-hook cap so a wedged daemon cannot hang the agent longer than 5s even if the relay's own deadline (§2.4) misbehaves. Confirm the field name and units in step 0 (V8); if per-hook timeout is unsupported in 2.1.224, drop the key — the relay's own deadline is the real protection.

**Why `settings.json` may still contain only documented Claude Code keys** (M1 §7.4): unchanged. `hooks` is a documented key. Nothing corral-specific goes in this file. Provenance stays in the sibling `meta.json`.

### 2.2 The merge question (M1's open item, now load-bearing)

M1 §7.4's verification note flagged it: nobody knows whether `--settings` `{"hooks": {...}}` **replaces** or **merges with** the user-level hook map. This matters two ways:

- If it **merges**, the developer's own hooks (this machine has a `caveman` plugin firing on `SessionStart`/`UserPromptSubmit` — see `spike/resume/NOTES.md` §4) run inside supervised sessions, adding latency and injecting context corral did not ask for. Tolerable, but must be a documented fact, and `corral doctor` should list foreign hooks.
- If it **replaces**, corral silently disables the user's hooks in supervised sessions. Also tolerable, but the user must be told, and `session.setting_sources` guidance changes.

**Step 0 V4 settles it.** Design branch:
- *Merges* → ship as written; add a startup INFO log naming foreign hook sources; add a `corral doctor` line. No behavior change.
- *Replaces* → ship as written, document loudly in README ("supervised sessions run corral's hooks only"), and add config `session.preserve_user_hooks` (default `false`) which, when true, reads `~/.claude/settings.json`, appends its hook entries after corral's, and records the merged result in `meta.json` for provenance.

Either way the *engine* is unaffected. Do not block §3–§6 on this.

### 2.3 Per-session secret

- Generated at **spawn** time: 32 bytes from `crypto/rand`, base64url, no padding. Regenerated on every spawn including resume — a secret is bound to a process, not to a session row.
- Held in `supervisor.secretRegistry` — an in-memory `map[sessionID]string` guarded by a mutex, entry deleted in `reap()`. **Never persisted, never logged, never returned by any API endpoint.** A daemon restart reaps or resumes every child (M1 §3.5), so a live child never outlives its secret's holder.
- Delivered to the child as `CORRAL_SESSION_SECRET` (the name M1 §7.2 reserved). `BuildEnv` gains a `secret string` parameter; its doc comment's "never copied from the snapshot" property is preserved — the value comes from the caller, not the environment.
- **Fallback if step 0 V10 shows hook commands do not inherit the claude process env:** write the secret to `<state_dir>/sessions/<id>/hook.secret` (0600, inside the existing 0700 dir) and append `--secret-file <path>` to the hook command. **Never put the secret literally in the command string** — `/proc/<pid>/cmdline` is world-readable on default Linux, whereas `/proc/<pid>/environ` is owner-only. Choose one mechanism at build time from the V10 result; do not implement a per-run fallback chain.

`ANTHROPIC_API_KEY` is already in `env_keys_json` as a *name only*; `CORRAL_SESSION_SECRET` joins it there. The M1 security test that greps the raw DB file for the API key value gains a sibling that greps for the secret value.

### 2.4 Transport: `corral hook-relay`

```
corral hook-relay --event <HookEventName> [--secret-file <path>]
  stdin:  the raw hook payload JSON, verbatim
  stdout: empty in M2 (see §2.5)
  exit:   always 0 (see below)
```

Sequence:
1. Read stdin fully, capped at 1 MiB. Over the cap → truncate, set `truncated: true`, continue (do not fail; the agent is blocked on us).
2. Read `CORRAL_SOCK`, `CORRAL_SESSION_ID`, `CORRAL_SESSION_SECRET`. Any missing → exit 0 silently (a hook fired from a non-corral session; not our business).
3. Generate `delivery_id` (uuidv4).
4. `POST http://unix/v1/hooks/events` over `CORRAL_SOCK` with a **hard total deadline** of `CORRAL_HOOK_TIMEOUT` (env, default `2s`).
5. On 2xx: decode the response envelope (§2.5); in M2 that is always `{}` → print nothing.
6. On **any** failure — dial refused, deadline, non-2xx, garbage body — write one line to stderr at most (`corral hook-relay: <err>`) and **exit 0**.

**Exit 0 always, unconditionally.** Rationale: a non-zero hook exit is a signal Claude Code interprets (blocking the tool, injecting stderr as context). Corral is an *observer* in M2; an observer that can break the agent when the daemon is down is a liability, not a feature. RUNBOOK §5.4's first invariant ("the daemon never crashes because of anything the agent does") has an unwritten dual, and this is it: **the agent never breaks because of anything corral does.** The only way corral influences the agent in M2 is `corral answer`, which is an explicit human act.

**No retries.** A retry doubles the time the agent is blocked and risks double-delivery. Instead, transitions are idempotent (§4.4). `delivery_id` exists for log correlation, not deduplication.

### 2.5 The response seam (why it exists, why it is inert)

The daemon's 200 body is `internal/hookrelay.Response`:

```json
{ "decision": null }
```

`decision`, when non-null, is a Claude Code hook JSON-output object which the relay prints verbatim to stdout. **In M2 the daemon always emits `{"decision": null}` and the relay always prints nothing.** The seam is exercised by one test (`TestRelayForwardsDecisionToStdout`, driven by an httptest server returning a canned decision) so that M4's auto-answer policy engine is a daemon-side change with zero relay changes. Confirm the exact JSON-output schema in step 0 V9; if it turns out that *any* stdout from a hook is interpreted (e.g. as `additionalContext`), the relay's "print nothing when decision is null" rule becomes load-bearing rather than merely tidy — test it explicitly.

### 2.6 Endpoint: `POST /v1/hooks/events`

Not under `/v1/sessions/{id}/` — the relay is a distinct principal with distinct auth, and a flat path keeps the auth middleware from being confused with the session-lookup middleware.

| Header | Value |
|---|---|
| `Corral-Api-Version` | `1` (existing middleware applies) |
| `Corral-Session-Id` | the session id from `CORRAL_SESSION_ID` |
| `Corral-Session-Secret` | the per-session secret |
| `Corral-Hook-Event` | the `--event` value |
| `Corral-Delivery-Id` | uuidv4 |
| `Content-Type` | `application/json` |

Body: the raw stdin bytes, **verbatim**, unparsed by the relay. The relay does not decode the payload — decoding untrusted JSON is the daemon's job, where it is fuzzed (§11) and where a panic is contained by an existing recover boundary rather than crashing inside the agent's hook.

Auth, in this order:
1. `Corral-Session-Id` present and known to `secretRegistry` → else `403 hook_unauthorized`. **Same error code and same response body for unknown-session and wrong-secret** — do not let an unauthenticated caller enumerate live session ids.
2. `subtle.ConstantTimeCompare([]byte(got), []byte(want)) == 1` → else `403 hook_unauthorized`.
3. Body ≤ 1 MiB (`http.MaxBytesReader`) → else `413 payload_too_large`.

Handler body, in full:
1. Auth (above).
2. `hookrelay.Decode(body)` → `HookPayload`. Decode failure is **not** an error response: the daemon records `hook.undecodable` with the raw (redacted, truncated) bytes and returns 200. Rationale: a CLI upgrade that changes a payload shape must degrade corral's *knowledge*, never the user's *agent*.
3. Non-blocking-ish enqueue onto the session's ingest channel (cap 256): `select { case ch <- ev: default: <block up to the handler's remaining deadline (500ms); then drop> }`. On drop: append `hook.dropped` event, set the session's `degraded` flag, log WARN. **Never lose an event without recording that it was lost.**
4. Return `200 {"decision":null}`.

Total handler latency at steady state is a mutex, a compare, and a channel send — sub-millisecond. The state machine runs asynchronously on the ingest goroutine, so a slow store write can never block the agent.

**Ordering.** One goroutine per session drains one channel; arrival order at the socket is the canonical order. Claude Code serializes most hooks (the agent is blocked on them), but parallel tool calls can produce concurrent `PreToolUse`s; for those, arrival order is arbitrary *and irrelevant*, because §4.3's tracker is keyed by `tool_use_id`, not by order. `events.seq` (AUTOINCREMENT) is the durable ordering record.

**Rejected alternatives.** *A second unix socket for hooks only* — more surface, no benefit; the version-handshake middleware and 0600 mode already exist on the one socket. *Fire-and-forget with no ack* — loses the backpressure signal and makes "did the hook reach the daemon?" untestable. *Relay does the state transition itself, writing SQLite directly* — puts a writer in the agent's process, breaks the single-writer store invariant, and makes ordering unresolvable.

## 3. Hook payload model

### 3.1 Types (`internal/hookrelay/payload.go`)

```go
// Common is the field set every hook payload is expected to carry.
// PROVISIONAL until step 0 V5.
type Common struct {
    HookEventName  string `json:"hook_event_name"`
    SessionID      string `json:"session_id"`
    TranscriptPath string `json:"transcript_path"`
    Cwd            string `json:"cwd"`
    PermissionMode string `json:"permission_mode"`
}

type HookPayload struct {
    Common
    // Tool events
    ToolName     string          `json:"tool_name"`
    ToolUseID    string          `json:"tool_use_id"`   // presence UNVERIFIED — step 0 V7
    ToolInput    json.RawMessage `json:"tool_input"`
    ToolResponse json.RawMessage `json:"tool_response"`
    // Notification
    Message string `json:"message"`
    Title   string `json:"title"`
    // SessionStart / Stop / PreCompact
    Source         string `json:"source"`            // startup|resume|clear|compact
    StopHookActive bool   `json:"stop_hook_active"`
    Reason         string `json:"reason"`            // SessionEnd
    Trigger        string `json:"trigger"`           // PreCompact: manual|auto
    // Preserved verbatim for forward compatibility and for the events row.
    Raw json.RawMessage `json:"-"`
}

func Decode(b []byte) (HookPayload, error)   // the fuzz target
```

`Decode` is total and defensive: unknown fields ignored (never `DisallowUnknownFields` — a CLI upgrade adding a field must not break ingest), wrong-typed fields tolerated by decoding into `json.RawMessage` where the shape is not corral's business, `Raw` always populated with the input bytes. It must never panic and never allocate unboundedly (nesting depth capped).

### 3.2 `state.HookEvent` — filling in M1's placeholder

M1 declared `state.HookEvent{Name string; Data map[string]any}`. M2 replaces the body, keeping the type name and the `Engine.OnHookEvent(ctx, sessionID, ev)` signature (that stability was the whole point of the seam):

```go
type HookEvent struct {
    Name        string                 // authoritative event name (see §3.3)
    SessionID   string                 // corral session id — from env, authoritative
    DeliveryID  string
    ReceivedAt  time.Time              // from Clock
    Payload     hookrelay.HookPayload
    RawRedacted []byte                 // redacted + truncated payload, what gets persisted
    Undecodable bool
    Truncated   bool
    IDMismatch  bool                   // §3.3
}
```

### 3.3 Identity and the mismatch rule

Two session identities arrive with every hook: `CORRAL_SESSION_ID` from the environment (used for routing and auth) and `session_id` inside the payload (claude's own). The spike proved they are equal for a main session across `--resume`. They will diverge for subagents (`Task` tool) if hooks fire in the subagent's context — step 0 V11 measures this.

**Rule: `CORRAL_SESSION_ID` is authoritative for routing, auth, and every state transition.** The payload's `session_id` is recorded as data. On mismatch, set `IDMismatch`, log WARN once per (session, payload-id) pair, and **still apply the transition**. Rationale: the secret is bound to the env id; honoring the payload id would let a subagent drive its parent's state (or, in a future where subagents are separate corral sessions, forge state for a session it does not hold a secret for). A subagent's hooks legitimately describe work the parent session is doing, so applying them to the parent is also semantically right in M2. `SubagentStop` is the event that tells us the subagent finished; it does **not** move the parent to idle (§4.2).

Same rule for the event name: if `--event` and `hook_event_name` disagree, trust `--event` (corral wrote it, the CLI did not), set a `name_mismatch` field on the persisted event, and log WARN. This is the tripwire for a payload-shape change in a CLI upgrade.

### 3.4 Redaction (`internal/redact`) — a §7 requirement landing here

RUNBOOK §7: "Event ingest runs a secret scan and redacts before persisting — the event store is append-only and long-lived; storing leaked credentials forever is a liability corral must not create. Redactions are marked in place, never silent."

M2 is the **first milestone that persists agent-supplied content** (`tool_input` for a `Bash` call is arbitrary user text and routinely contains `export TOKEN=...`). So `internal/redact` lands here.

```go
type Marker struct{ Rule string; Offset, Len int }
func Redact(b []byte) ([]byte, []Marker)
```

Rules v1 (each a named regexp, table-driven, one test case per rule with a positive and a negative):
`anthropic_key` (`sk-ant-[A-Za-z0-9_\-]{20,}`), `openai_key` (`sk-[A-Za-z0-9]{32,}`), `github_token` (`gh[pousr]_[A-Za-z0-9]{36,}`), `aws_access_key` (`AKIA[0-9A-Z]{16}`), `slack_token` (`xox[baprs]-[A-Za-z0-9-]{10,}`), `private_key_block` (`-----BEGIN [A-Z ]*PRIVATE KEY-----`), `assignment` (`(?i)(api[_-]?key|token|secret|password|passwd|bearer)\s*[=:]\s*["']?[A-Za-z0-9_\-\.]{16,}`), `jwt` (`eyJ[A-Za-z0-9_\-]{10,}\.[A-Za-z0-9_\-]{10,}\.[A-Za-z0-9_\-]{10,}`).

Replacement is in-place-marked: `«redacted:anthropic_key»`. Markers are recorded on the event row as `redactions: [{rule, offset, len}]` so an auditor can see that something was removed and why.

Applied to `RawRedacted` before `AppendEvent`, and to every string that reaches a `BlockedReason` (§5) or a notification body (§8). **Not** applied to the in-memory payload used for transition logic — redaction is a persistence and egress concern, not a semantics concern.

Truncation: `RawRedacted` capped at `state.max_event_payload_bytes` (default 64 KiB). A `Write` tool's `tool_input` can be a whole file; the events table is append-only forever. On truncation set `truncated: true` and keep the head.

## 4. The state machine

### 4.1 States

`session.AgentState` gains four values; the M1 four stay (the API shape does not change, per M1 §9.2's promise):

| Value | Meaning | Source |
|---|---|---|
| `starting` | spawned, no hook yet | process |
| `working` | agent is producing / running tools | hooks |
| `blocked` | agent needs a human; `blocked_reason` is populated | hooks |
| `idle` | turn finished, waiting for a prompt | hooks |
| `exited` | process gone | process |
| `failed` | spawn failed / unresumable | process |
| `unknown` | live process, but corral cannot say (see §4.5) | derived |

**Precedence.** Process reality outranks hook belief:

```
if status ∈ {exited, failed}          → agent_state = exited|failed   (hook state discarded)
if status == stopping                 → agent_state = exited          (draining)
if status ∈ {starting, running}       → agent_state = hook-derived state
   ... but if no hook has EVER arrived and now-spawn > first_hook_grace → unknown
```

This is the rule that keeps a `Stop`-then-crash session from rendering `idle` forever.

### 4.2 Transition table

Pure function, `internal/state/machine.go`, zero I/O, exhaustively table-tested (event × every state):

| Hook event | Effect | Notes |
|---|---|---|
| `SessionStart` | → `idle` | Clears pending-tool tracker and blocked reason. `source` recorded (`startup`/`resume`/`clear`/`compact`). This is also corral's proof that hooks are wired — the absence of it within `first_hook_grace` is what makes §4.5 fire. |
| `UserPromptSubmit` | → `working` | Clears blocked reason. |
| `PreToolUse` | → `working`; **add** to pending-tool tracker | The heartbeat *and* the structured record of what tool is about to run. Load-bearing for §5. |
| `PostToolUse` | → `working`; **remove** from pending-tool tracker | If it clears the last pending entry while blocked, → `working` and clear the reason (the human answered). |
| `Notification` | see §5 — → `blocked(reason)` **iff** the tracker is non-empty; otherwise **no transition** | The classifier. Never parses message text to decide state. |
| `Stop` | → `idle`; clear tracker and reason | Turn boundary. |
| `SubagentStop` | → `working` (heartbeat only) | **Explicitly not `idle`.** The parent is still mid-turn; treating a subagent's finish as the session's finish is the single most likely wrong transition in this table. |
| `PreCompact` | → `working` | Compaction is work. |
| `SessionEnd` | no state change; record `reason` | The process reaper is authoritative for `exited`. Emitting `exited` here would race `cmd.Wait()` and could mark a session dead that is about to be resumed. |
| *undecodable / unknown name* | no state change; bump `last_hook_at_ms` | An unknown future hook event is still proof of life. |

Every transition, whether or not the state changes, updates `last_hook_at_ms` and `hook_count`.

### 4.3 Pending-tool tracker (`internal/state/pending.go`)

Per session, in memory (rebuilt from `SessionStart` on resume; a resumed session starts empty, which is correct):

```go
type PendingTool struct {
    ToolUseID string
    ToolName  string
    ToolInput json.RawMessage   // redacted copy kept for the reason payload
    At        time.Time
}
type Pending struct { /* ordered map keyed by ToolUseID, newest last */ }
```

**Keyed by `tool_use_id`, not a single slot.** Parallel tool calls are routine — a turn issuing three `Read`s in one message produces three `PreToolUse` hooks before any `PostToolUse`. A single-slot tracker would name the wrong command in the notification, which is worse than naming none.

**If step 0 V7 shows `tool_use_id` is absent from the payload:** fall back to an ordered list keyed by a synthetic id, matching `PostToolUse` to the oldest pending entry with the same `tool_name` and byte-equal `tool_input`. Unmatched entries are evicted after `state.pending_tool_ttl` (default 30m) so a lost `PostToolUse` cannot pin a session in `blocked` forever. The TTL sweep is lazy — evaluated on the next hook or the next `State()` read, no goroutine.

### 4.4 Idempotency and ordering

The relay never retries, so duplicates are not expected. They are nonetheless harmless **by construction**, and that is the design position rather than a dedupe cache:

- Every transition is a total function of (current state, event) to a target state — replaying `Stop` twice yields `idle` twice.
- Tracker operations are set semantics: adding an existing `tool_use_id` overwrites; removing an absent one is a no-op.
- Blocked reasons **replace**, never accumulate.
- The only non-idempotent action is the notification, and it is debounced (§8.4).

Out-of-order arrival (only possible among concurrent `PreToolUse`s) is likewise safe because the tracker is a keyed set. A `PostToolUse` arriving before its `PreToolUse` removes nothing and then the late `PreToolUse` adds a phantom entry — bounded by the TTL, logged at DEBUG, and impossible in practice since the CLI blocks on the pre-hook before running the tool.

### 4.5 Staleness and degradation — derived, no timers

**There is no sweeper goroutine and no timer.** Staleness is computed at render time from persisted timestamps:

```
stale        := agent_state ∈ {working} && Clock.Now() - last_hook_at_ms > state.stale_after       (default 15m)
never_hooked := hook_count == 0 && Clock.Now() - started_at_ms > state.first_hook_grace            (default 60s)
degraded     := stale || never_hooked || <hook.dropped occurred since last transition>
```

- `never_hooked` → `agent_state` renders `unknown`, and `corral ls` appends `(hooks not firing?)`. This is the failure that matters most: a user whose global settings broke the pin gets told, instead of silently seeing `starting` forever.
- `stale` → state is still `working`, rendered as `working?`. Never lie; a long `Bash` build legitimately produces no hooks for an hour.
- **`blocked` never goes stale.** Blocked genuinely lasts until a human acts; a timeout would be an invention.

Why no goroutine: timers are the #1 source of flaky tests (RUNBOOK §5.4 forbids sleep-synchronized tests), and rendering-time derivation needs only the injected `Clock`, which `clocktest.FakeClock` already controls. Degradation is a *rendering* concern, so it is deliberately **not** event-sourced — nothing is appended when a session becomes stale.

### 4.6 Persistence

**Both a column and events, with different jobs.**

- **Columns on `sessions`** (`agent_state`, `agent_state_since_ms`, `blocked_reason_json`, `last_hook_at_ms`, `hook_count`) are the hot read for `corral ls` and the thing that survives a daemon restart so a phone notification's deep link still resolves. Written by the ingest goroutine inside `UpdateSession`.
- **`events` rows** are the audit/replay source of truth: `hook.received` for every hook (with the redacted payload), `state.transition` for every state change (with `{from, to, reason, hook_seq}`), plus `hook.dropped` / `hook.undecodable` / `hook.unauthorized`.

New event kinds (append to `session.EventKind`; existing kinds are never renamed):
`hook.received`, `hook.dropped`, `hook.undecodable`, `hook.unauthorized`, `state.transition`, `notify.sent`, `notify.failed`, `notify.dropped`, `notify.suppressed`, `session.answered`.

`hook.received` at one row per hook is high-volume (a busy turn is ~20 hooks). Bound it: config `state.persist_hook_events` (default `"transitions"`), values `all` | `transitions` | `none`. Default persists `hook.received` **only when the hook caused a state change or carried a blocked reason**; the rest bump the counters without a row. `all` is the debugging/dogfooding setting and is what step 0 and the contract suite run with. This keeps the append-only store from growing without bound while preserving a complete transition history.

**On daemon restart / resume**, the engine resets the in-memory tracker and sets `agent_state = starting`, then waits for the resumed session's `SessionStart` hook. The persisted column is not trusted as live state after a respawn — it is history.

**Rejected: derive state by replaying events on every read.** `corral ls` is called constantly and would become O(events). Rejected: **keep state only in memory.** A daemon restart would drop the blocked reason, which is precisely the payload the notification deep-links to.

## 5. Blocked-reason parsing

### 5.1 The mechanic (this is the moat)

The `Notification` payload does **not** carry a tool name or tool input. It carries `message` (human prose) and the common fields. Parsing that prose to learn which command needs approving is terminal-scraping relocated one layer up, and it breaks on the next CLI copy edit.

The structured signal is elsewhere and corral already has it:

```
PreToolUse { tool_name: "Bash", tool_input: {command:"npm test"} }   ← structured, arrives first
        ↓  (the CLI renders its permission dialog; no PostToolUse will come until a human acts)
Notification { message: "Claude needs your permission to use Bash" } ← "a human is needed"
```

**Rule: `Notification` is the *trigger*; the dangling `PreToolUse` set is the *content*.** Message text becomes the human-readable `summary` and nothing else. This is also the structural discriminator against the CLI's ~60-second "Claude is waiting for your input" nudge: that nudge arrives with an **empty tracker** (the turn already ended with `Stop`), so it produces **no transition** — just a `hook.received` row. No string matching decides state, ever.

### 5.2 Kind, derived from the dangling tool name

| Dangling `tool_name` | `kind` | Extracted |
|---|---|---|
| `ExitPlanMode` | `plan_approval` | `tool_input.plan` (truncated to 2 KiB for the summary) |
| `AskUserQuestion` | `question` | `tool_input` question + options array, verbatim |
| anything else | `permission` | `tool_name` + `tool_input` |
| *(tracker empty)* | — | no transition; `hook.received` only |
| *(reserved)* | `api_error` | **M4** — no hook fires for this; see §0 |
| *(fallback)* | `unknown` | tracker non-empty but tool name unrecognized and input undecodable |

**Ambiguity is reported, not guessed.** If the tracker holds more than one entry when `Notification` arrives, all entries go into `tools[]` (newest first) and `ambiguous: true` is set. `corral ls` renders the newest; the notification body says "one of 2: `npm test`, `rm -rf build`". Naming the wrong command confidently is worse than naming two.

### 5.3 Schema (`internal/state/reason.go`, persisted in `blocked_reason_json`, exposed in the API)

```json
{
  "kind": "permission",
  "summary": "permission to run `npm test`",
  "message": "Claude needs your permission to use Bash",
  "tools": [
    { "tool_use_id": "toolu_01…", "tool_name": "Bash",
      "tool_input": {"command": "npm test"}, "at": "2026-08-08T14:03:11Z" }
  ],
  "ambiguous": false,
  "confidence": "correlated",
  "source_event": "Notification",
  "at": "2026-08-08T14:03:12Z",
  "hook_seq": 4711,
  "redactions": [{"rule":"assignment","offset":42,"len":37}]
}
```

- `confidence`: `"correlated"` (Notification + exactly one dangling tool), `"ambiguous"` (Notification + several), `"opaque"` (Notification, tracker non-empty, input undecodable). There is no `"inferred"` value in M2 — see below.
- `summary` is the one line a phone notification shows. Built by a small per-kind formatter: `permission` → ``permission to run `<first 80 chars of a Bash command | tool_name + first input key>` ``; `plan_approval` → `"approval of a plan (<n> steps)"`; `question` → the question text truncated to 100 chars.
- `tool_input` is **redacted** (§3.4) before it lands here, because this object is persisted *and* egressed to a third-party notification server.

**What stays opaque, stated plainly:** the CLI's permission dialog options (which number means approve, whether "don't ask again" is offered) are not in any hook payload. Corral knows *what* is being asked and *that* a human is needed; it does not know the shape of the answer widget. That is the honest boundary of M2, and it is why `corral answer` delivers literal text (§7.2).

**Rejected: inferring `blocked` from a stalled `PreToolUse` alone** (no `PostToolUse` for N seconds). Tools legitimately run for minutes; any threshold either fires false positives on a slow build or misses fast prompts. If step 0 V15 shows the permission `Notification` is *delayed* rather than immediate, revisit — but ship the Notification-driven path first and gather data during dogfooding rather than guessing a threshold now.

### 6.1 DDL — `migrations/0002_agent_state_and_name_scope.sql`

Two changes: the new state columns, and M1 known-limitation #2 (session names reserved forever because `sessions.name` is inline-`UNIQUE` and rows are never deleted).

```sql
    WHEN 'starting' THEN 'starting'

```

**Why that predicate, precisely.** A session at `desired_state='running', status='exited'` is M1's graceful-shutdown state (§3.6 leaves the intent as `running` so recovery resumes it). That session is **not** terminal and its name must stay reserved — it is about to come back. Only a session that was explicitly killed (`desired_state='stopped'`) *and* is actually dead frees its name. Nothing else expresses that.

Migrating `running` → `agent_state='starting'` rather than `'working'` is deliberate: a pre-M2 row has no hook history, and the M1 daemon that wrote it is gone, so the session will be resumed and will re-announce itself via `SessionStart`.

### 6.2 The foreign-key trap, and the fix

`events.session_id REFERENCES sessions(id) ON DELETE CASCADE`. `DROP TABLE sessions` runs an implicit `DELETE FROM`, which **fires the cascade and destroys the entire event log** when foreign keys are enabled. And `PRAGMA foreign_keys` is a **no-op inside a transaction**, which is exactly where the migration runner executes. `PRAGMA defer_foreign_keys` does not help either — it defers *checks*, not *actions*.

**Fix: run migrations on a separate, short-lived `sql.DB` opened with `_pragma=foreign_keys(OFF)`, close it, then open the real store with `foreign_keys(ON)` as today.** One localized change in `store.Open`; no dependence on a pooled connection never being recycled, no per-migration directives, no reordering of pragmas. The migration test asserts the events table is intact afterward, which is the regression guard.

**Rejected: rename-on-kill** (append `~<n>` to a terminal session's name so the UNIQUE constraint stops blocking reuse). Avoids the rebuild but mangles historical names in `corral log` and `events`, and leaves a schema wart that every later milestone inherits. The rebuild is a one-time cost with a test that makes it safe.

### 6.3 Migration test (RUNBOOK §5.3)

`internal/store/migrate_0002_test.go`, using the existing `testdata/db/v1.db` fixture:

1. Copy `testdata/db/v1.db` to a temp path; snapshot every `sessions` row and every `events` row via raw SQL before migrating.

4. **Assert `events` row count and contents are unchanged** — the FK-cascade regression guard.

6. Assert the partial unique index: inserting a second row with an existing *active* session's name fails; inserting one reusing a `(stopped, exited)` session's name succeeds; a `(running, exited)` session's name is still reserved.
7. Generate and check in `testdata/db/v2.db` (a populated post-M2 fixture) for M3's migration test.

## 7. `corral answer`

### 7.1 API

```
POST /v1/sessions/{idOrName}/answer
  { "text": "1", "newline": true, "key": "" }
  → 200 <Session>
```

Exactly one of `text` or `key` must be set. Errors: `session_not_found` (404), `session_not_live` (409 — M3 adds auto-wake), `bad_request` (400).

CLI: `corral answer <session> "text"`, plus `corral answer <session> --key enter|esc|up|down|tab|ctrl-c` and `--no-newline`.

### 7.2 Delivery mechanics (interactive / PTY)

`supervisor.WriteInput(ctx, idOrName, []byte) error` writes to `ls.PTYMaster` under the registry lock — the same fd `attach.go` already writes `Input` frames to, so an attached client and an `answer` cannot interleave mid-byte.

Encoding rules:
- **Single-line `text`** → the literal UTF-8 bytes, then `\r` (unless `--no-newline`). This is byte-identical to a human typing it.
- **Multi-line `text`** → wrapped in bracketed paste (`ESC[200~` … `ESC[201~`) then `\r`. The TUI enables `?2004h` at startup (confirmed in the M0 capture), so without brackets each embedded newline would submit a separate turn.
- **`key`** → a fixed lookup table (`enter`→`\r`, `esc`→`\x1b`, `up`→`ESC[A`, `down`→`ESC[B`, `tab`→`\t`, `ctrl-c`→`\x03`). Unknown names are rejected at the API, not silently dropped.

**Payload is data, never shell-interpolated** (§7 security baseline). There is no shell anywhere on this path — CLI arg → JSON body → `[]byte` → `write(2)`. The security test sends `"; rm -rf / #$(whoami)`&& echo pwned"` and asserts fakeclaude read those exact bytes from stdin.

### 7.3 Semantic approve/deny — verification-gated, not decided from memory

The obvious sugar is `corral answer <s> --approve` for a permission block. The obvious objection is that guessing which dialog option means "approve" is the heuristic corral exists to avoid, and the dialog differs across tools.

**Do not decide this from recall.** Step 0 V16 measures it: for each of `Bash`, `Write`, `ExitPlanMode`, `AskUserQuestion`, is the approve option always the first, and is `1` + Enter always the way to select it?

- **If it verifies uniformly** → ship `--approve` as documented sugar for `"1"`, and put `corral answer <name> --approve` in the notification body. The demo needs this: a phone user must not have to guess a magic number.
- **If it does not** → drop the sugar, document why in known limitations, and have the notification body carry the literal hint `corral attach <name>`. M4's structured permission-decision path (a hook response, not a keystroke) is the real fix either way.

### 7.4 Interaction with state — answer never forces a transition

`answer` appends `session.answered` (with the redacted text length, **never the text**) and writes the bytes. It **does not** set `agent_state`. The session leaves `blocked` when the next hook proves it did: `PostToolUse` (the tool was approved and ran) or `UserPromptSubmit`/`Stop` (the question was answered). If no hook arrives, the session correctly stays `blocked` — corral reports what it knows, not what it hopes.

This is the property the integration test asserts explicitly (`TestAnswerDoesNotForceTransition`): write the answer, assert state is still `blocked`, then have the scenario fire `PostToolUse`, then assert `working`.

## 8. Notifier

### 8.1 Interface (`internal/notify`)

```go
type Notification struct {
    SessionID   string
    SessionName string
    Cwd         string
    Event       string        // "blocked" | "exited"
    ReasonKind  string        // BlockedReason.Kind
    Summary     string        // one line, already redacted
    Detail      string        // multi-line body, already redacted
    Hint        string        // e.g. `corral answer api-refactor "1"`
    At          time.Time
}

type Notifier interface {
    Name() string
    Send(ctx context.Context, n Notification) error
}

type Dispatcher struct{ /* bounded queue, backends, Clock, store, log */ }
func (d *Dispatcher) Notify(n Notification)   // NEVER blocks, never errors
```

`Engine` holds a `*Dispatcher` and calls `Notify`. That method's only possible actions are a non-blocking channel send or a drop — **the type system is what guarantees "a failed notification never blocks the state machine"** (RUNBOOK §5.3), not discipline.

### 8.2 Backends

**ntfy** — `POST {server}/{topic}`, body = `Detail`, headers `Title`, `Priority`, `Tags: warning`, and `Authorization: Bearer <token>` when configured.

*On auth in v1:* the token is **supported and strongly recommended**, not omitted. An ntfy topic is a URL anyone can subscribe to; the payload contains session names, cwd paths, and shell commands. Shipping "no auth in v1" would mean shipping a default that leaks a developer's command lines to anyone who guesses a topic. Default is empty (anonymous), and the daemon logs one WARN at startup when `ntfy.enabled && token == ""`.

**webhook** — `POST {url}` with `Content-Type: application/json`, body = the `Notification` struct marshaled, plus any configured static headers. Headers are secret-class config: never logged, never returned by `/v1/config` (masked as `***`).

Both share one `http.Client` with `Timeout: notify.timeout` (default 10s) and no proxy-from-environment (the daemon env is frozen and audited; honoring `HTTP_PROXY` would be an unaudited egress path).

### 8.3 Trigger

Fired by the Engine **on the transition into `blocked`** — the edge, not the level. `notify.on` (default `["blocked"]`) may also include `"exited"` (nonzero exit code only). Nothing else notifies in M2.

### 8.4 Debounce and delivery policy

- **Debounce:** suppress if a notification with the same `(session_id, reason_kind, summary)` was sent within `notify.debounce` (default 30s). A flapping block (answer → immediate re-block on the next tool) is real information, but an identical repeat inside 30s is noise. Suppressions append `notify.suppressed`.
- **Queue:** cap 128. Full → drop, append `notify.dropped`, log WARN. Never block.
- **Retries:** 3 attempts with backoff 1s/4s/16s **driven by the injected Clock** (so tests advance time instead of sleeping). Retry only on transport errors and 5xx; a 4xx is a config error and is not retried. Exhausted → append `notify.failed` with the last error.
- Success → append `notify.sent` with backend name and attempt count.

### 8.5 Payload content

```
Title: corral/api-refactor blocked
Body:  permission to run `npm test`

       repo: ~/code/x
       answer: corral answer api-refactor "1"
       attach: corral attach api-refactor
```

No URL in M2 (the dashboard is M5). Everything in the body has passed `redact.Redact` (§3.4) — this is corral's only egress to a third party and the redactor's most important call site.

### 8.6 The reply path (exit-criteria-mandated, sequenced last)

RUNBOOK M2's exit criteria are literally "…answer from the phone via ntfy reply → agent continues." Without an inbound path there is no M2. The TCP listener is M5. The mechanism that closes the gap with **zero inbound ports** is an outbound long-poll: the daemon subscribes to an ntfy topic (`GET {server}/{reply_topic}/json`, streaming) and treats published messages as `answer` calls.

Threat model, in one paragraph: anyone who can publish to the reply topic can type arbitrary text into a live agent's PTY. That is a remote-input capability, so it is off by default and gated three ways: (1) `notify.ntfy.reply.topic` **must differ** from the notify topic — the daemon refuses to start otherwise, so a guessable read topic never grants write access; (2) `notify.ntfy.reply.token` is **required** when the reply subscriber is enabled — no anonymous reply topics; (3) every message must be `<session-name> <text>` and is rejected unless the named session exists, is live, and is currently `blocked`. Messages are rate-limited (10/min), never shell-interpreted, and every accepted reply appends `session.answered` with `via: "ntfy"`. Subscriber reconnects with backoff on stream drop.

Sequenced as the **last** implementation step so it can slip a release without blocking the engine.

### 8.7 Config keys

```toml
[notify]
enabled  = false
on       = ["blocked"]        # subset of ["blocked","exited"]
debounce = "30s"
timeout  = "10s"
retries  = 3

[notify.ntfy]
enabled  = false
server   = "https://ntfy.sh"
topic    = ""
token    = ""                 # secret
priority = "default"

[notify.ntfy.reply]
enabled = false

token   = ""                  # secret; required when enabled

[notify.webhook]
enabled = false
url     = ""

```

**Repo trust boundary: the entire `[notify]` and `[state]` trees are user-file/env only.** Add every key to `repo_allowlist.go`'s rejection list. This is not bookkeeping — a cloned repo's `.corral.toml` setting `notify.webhook.url` would exfiltrate every blocked reason (including redaction-missed command lines) to an attacker, and setting `notify.ntfy.reply.topic` would hand an attacker keystroke access to the PTY. A test asserts a repo file setting either key is rejected with a WARN.

## 9. fakeclaude scenario engine v1

### 9.1 Format: JSON, not YAML

RUNBOOK §5.1 sketches YAML. **Deviation, recorded here in one sentence: scenarios are JSON**, because YAML would add the milestone's only new dependency for a file format that is as often machine-generated as hand-written, and `encoding/json` is already everywhere. The sketch's step vocabulary is preserved.

`testdata/scenarios/<name>.json`, selected by `CORRAL_FAKE_SCENARIO` (the env var M1 reserved and ignored):

```json
{
  "name": "blocked_permission",
  "steps": [
    {"op":"emit_tui",    "text":"› npm test"},
    {"op":"fire_hook",   "event":"SessionStart",     "payload":{"source":"startup"}},
    {"op":"wait_stdin",  "match":"^.+\r$", "capture":"prompt", "timeout":"10s"},
    {"op":"fire_hook",   "event":"UserPromptSubmit", "payload":{"prompt":"{{prompt}}"}},
    {"op":"fire_hook",   "event":"PreToolUse",       "payload":{"tool_name":"Bash","tool_use_id":"toolu_01","tool_input":{"command":"npm test"}}},
    {"op":"fire_hook",   "event":"Notification",     "payload":{"message":"Claude needs your permission to use Bash"}},
    {"op":"wait_stdin",  "match":"^1\r$", "capture":"answer", "timeout":"30s"},
    {"op":"fire_hook",   "event":"PostToolUse",      "payload":{"tool_name":"Bash","tool_use_id":"toolu_01","tool_response":{"stdout":"ok"}}},
    {"op":"fire_hook",   "event":"Stop",             "payload":{"stop_hook_active":false}},
    {"op":"exit",        "code":0}
  ]
}
```

Verb list is deliberately five: `emit_tui`, `fire_hook`, `wait_stdin`, `emit_stdout_jsonl` (declared, unimplemented — the M4 seam), `exit`. **No `sleep` verb** — RUNBOOK §5.4 forbids sleep-synchronized tests, and every wait here is on stdin, which is an actual event.

`{{capture}}` interpolation is a literal string substitution into payload string values only.

### 9.2 `fire_hook` executes the *real* pinned hook command

This is the highest-value property of the engine. On `fire_hook`, fakeclaude:

1. Reads the file passed to `--settings` (it already parses and records it in M1).
2. Looks up `hooks.<event>[].hooks[].command` — **the exact command string corral wrote**.
3. Merges the scenario's `payload` over the common fields fakeclaude fills in itself (`hook_event_name`, `session_id` from `--session-id`/`--resume`, `transcript_path` from `internal/claude/sessions` under `CORRAL_FAKE_HOME`, `cwd`, `permission_mode`).
4. Runs the command **via `sh -c`** — because Claude Code runs hook commands through a shell. Exec'ing it directly would make fakeclaude lie in exactly the dimension the contract suite exists to catch (quoting of the absolute binary path, `$VAR` handling, etc.).
5. Feeds the merged payload JSON on the hook's stdin; captures exit code, stdout, stderr, and wall duration into `$CORRAL_FAKE_STATE/<session-id>/hooks-<N>.json`.

That recording is what lets tests assert the relay was **inert** (`exit == 0`, `stdout == ""`) and **fast** (`duration < hook_timeout`) — i.e. that corral did not perturb the agent. It also means a broken settings.json, a missing binary, or a lost `CORRAL_SESSION_SECRET` fails a test rather than passing silently.

fakeclaude does **not** get a bespoke HTTP client. It knows nothing about `/v1/hooks/events`.

### 9.3 M2 scenario set

`smoke_turn` (SessionStart → prompt → tools → Stop), `blocked_permission` (above), `blocked_plan` (`ExitPlanMode`), `blocked_question` (`AskUserQuestion`), `parallel_tools` (three `PreToolUse`, then Notification → `ambiguous: true`), `idle_nudge` (Stop, then a Notification with an empty tracker → **no transition**), `hook_auth_forged` (fires the hook command with `CORRAL_SESSION_SECRET` stomped → expect the relay to still exit 0 and the daemon to record `hook.unauthorized`), `undecodable_payload` (garbage stdin), `no_hooks_at_all` (scenario fires nothing → session renders `unknown` after `first_hook_grace` on the fake clock).

## 10. Contract tests (RUNBOOK §5.3, land in M2)

`test/contract/` — a table of cases, each with two drivers and **one shared set of assertions**.

```go
type Case struct {
    Name       string
    Scenario   string          // testdata/scenarios/<name>.json  (fake driver)
    Prompt     string          // what to type into real claude    (real driver)
    Expect     Expectations
}
type Expectations struct {
    HookSubsequence []string          // e.g. UserPromptSubmit, PreToolUse, PostToolUse, Stop
    RequiredFields  map[string][]string // event name → fields that must be present & non-empty
    StateTimeline   []session.AgentState // e.g. starting, working, idle
    BlockedKind     string
}
```

**Assertions are shape assertions, not equality.** `HookSubsequence` must appear *as a subsequence* of what the daemon received — real claude emits extra hooks (`PreCompact`, extra `PreToolUse` for reads we didn't ask for) and a strict-equality assertion would be permanently red. `StateTimeline` likewise asserts the expected transitions appear in order, ignoring repeats.

Both drivers produce the same observation object by reading the daemon's own `events` table (`GET /v1/sessions/{id}/events`), so the assertion code physically cannot special-case the fake. Divergence prints a unified diff of the two hook traces — "fakeclaude is lying" becomes a mechanical fix rather than an investigation.

**Gating and cost control.** Default `go test ./...` runs the fakeclaude driver only. `CORRAL_CONTRACT=1` additionally runs the real driver, which: uses `--model haiku`; runs in a fresh `t.TempDir()` git repo with a pinned settings file so behavior does not depend on the developer's global config (spike finding #3); has a per-case wall budget (`CORRAL_CONTRACT_TIMEOUT`, default 120s) after which the case fails rather than hanging; and is limited to **three cases** (`smoke_turn`, `tool_use`, `blocked_permission`). CI runs it nightly and on a `claude`-version-change trigger, never on push. Estimated cost: a few cents per run.

Provoking a real permission block deterministically is itself uncertain (a pinned settings file with no allow rules should make a `Bash` call prompt in TUI mode) — **step 0 V21** measures it; if it is not deterministic, the third case is dropped from the real driver and marked fake-only with a comment saying why, rather than being left flaky.

## 14. Known limitations to record at the end of M2

1. **`api_error` blocked reason is not produced** — no hook fires for it; M4's stream-json closes this (§0).
2. **Corral knows what is being asked, not the shape of the answer widget** — `answer` delivers literal text/keys; structured permission decisions are M4 (§5.3).
3. **Subagent hooks are attributed to the parent session** — correct for M2's single-session model, revisited when M4 makes agent-spawned agents first-class (§3.3).
4. **A blocked session never times out** — deliberate; a human is genuinely required (§4.5).
5. **Staleness is a rendering concern and is not event-sourced** — `corral log` will not show "went stale at T" (§4.5).
6. **The relay is invisible by design and therefore fails silently** — a wedged daemon means hooks stop being recorded and the session renders `unknown` after `first_hook_grace`; it does not break the agent (§2.4).
7. **The ntfy reply path grants remote keystroke access to a live PTY** — off by default, three gates, documented threat model (§8.6).
8. Anything step 0 turns up that this document guessed wrong.
