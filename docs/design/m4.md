# corral M4 design — headless orchestration (task DAGs)

**Milestone goal (RUNBOOK.md:156-168):** corral runs headless Claude Code
sessions non-interactively (`-p --output-format stream-json`), models work as a
DAG of tasks with dependencies/retries/per-task worktree isolation, parses the
stream-json protocol for turns/tool-use/result/cost, and accounts cost per task
and per DAG. **Exit criterion (RUNBOOK.md:168):** a 3-node DAG
(plan → implement → review) runs unattended with `fakeclaude`; with real
`claude` behind an env-var gate.

M4 is the largest milestone by surface area. This doc scopes **v0.4.0 to the
exit criterion** — the spine that makes a 3-node DAG run unattended — and
explicitly defers (with sequencing, not silence) everything the exit criterion
does not require. The m3.md discipline: write the deferrals down so they are not
lost (§14).

## 0. What already exists (do not rebuild)

Grounding in the real tree (verified via source read + the M0 spike record, not
memory):

- **Session mode is declared but decorative.** `session.Mode` has
  `ModeInteractive` and `ModeHeadless` (`session/spec.go:10-15`,
  "reserved for a later milestone"). `BuildArgv`/`Spawn` **ignore** `Spec.Mode`
  — every spawn is a PTY TUI. The API **hard-rejects** non-interactive mode
  (`handlers_sessions.go:266-268`, `CodeUnsupportedMode`). M4 makes
  `ModeHeadless` real; it does not invent the enum.
- **`Spec.ExtraArgs` is a dead field** (`spec.go`, "reserved; empty in M1") —
  never consumed by `BuildArgv`. This is the designed seam for headless flags,
  but M4 does **not** route `-p`/`--output-format` through a generic
  passthrough — those are first-class (§5), because they change the *spawn
  mechanism* (pipe vs PTY), not just argv.
- **Spawn is PTY-only.** `Spawn` (`spawn.go:218`) always `pty.StartWithSize`
  (Setsid+Setctty, PGID==PID). There is **no pipe path**. `output.log`
  (`screen/outputlog.go`) is a size-capped RAW PTY tee (escape sequences,
  diagnostics only) — the stream-json runner **cannot** reuse it; it needs its
  own structured stdout capture off a pipe.
- **A working headless reference exists.** M0 spike `spike/verify/main.go`
  (`cmdV3`, ~:345) ran `claude -p --output-format stream-json --verbose
  --include-partial-messages` under `Setsid`, captured off `cmd.StdoutPipe()`,
  SIGTERM to the pgroup. This is the pattern §5 productionizes.
- **`claude -p` writes the standard transcript.** spike-notes.md:47-48 + the
  captured `spike/verify/out/*.jsonl`: `-p` runs write
  `~/.claude/projects/<cwd "/"→"-">/<session_id>.jsonl`, append-only, filename
  == in-file session id (13/13). **Consequence:** headless sessions are
  `Resumable` (`checkpoint/resume.go:185`) via the *same* `--resume` path,
  `LastRecordIsCompletedTurn` (`turnboundary.go:47`) is meaningful for headless
  (its backward-scan already skips the `type:"last-prompt"` record that leads
  the file), and M3's checkpoint/reaper machinery applies unchanged. M4 does
  **not** fork the resume/turn-boundary logic for headless.
- **`--permission-mode` is resolved+persisted but never delivered to the
  child** (not in `BuildArgv`, not in `settings.Pin`). A latent gap; §5 closes
  it. It lives in `config/repo_allowlist.go`'s user/env-only set today — that
  boundary is load-bearing once `-p` makes `bypassPermissions` reachable.
- **Store: `user_version`-gated embedded migrations**, latest `0003_activity`.
  events table: `seq PK, session_id (NULL=daemon-scoped, ON DELETE CASCADE),
  ts_ms, kind, data_json` — opaque JSON, **no kind index, no query-by-kind**.
  `sessions_name_active` (0002) is a **partial unique index on `name`** keyed to
  non-terminal rows — a terminal `(desired_state='stopped', status IN
  (exited,failed))` row frees its name (proven by
  `TestWake_NameCollisionErrors`). No tasks/DAG/cost table exists. M4 adds
  `0004_*.sql`.
- **Auth: only the hooks route is authenticated** (`Corral-Session-Secret`
  header, `crypto/subtle.ConstantTimeCompare`, `handlers_hooks.go:53-61`). The
  rest of the HTTP API relies on the unix socket + `Corral-Api-Version`
  handshake — **no bearer auth exists**. "Agents spawning agents" (scoped
  tokens) needs a new middleware; deferred (§14).
- **Config trust boundary** (`config/repo_allowlist.go:17`): a repo
  `.corral.toml` may set only `session.{model,scrollback_lines,term}`;
  everything else is dropped + reported as a `Rejection`. **M4's budgets and
  (deferred) auto-answer allowlists are user/env-only**, resolved by a
  dedicated pipeline like `[state]`/`[notify]`.
- **API wiring seam**: `RegisterMeta/Sessions/Hooks/Attach` + `Deps` structs
  (`daemon.go:368-389`). M4 adds `RegisterTasks`.
- **Notify/answer is inherently interactive.** `answer/answer.go` `Encode`
  returns literal PTY bytes (bracketed-paste). No stream-json answer encoder
  exists. The blocked flow builds a rich `state.BlockedReason`
  (`state/reason.go:8-26`). Headless permission handling in v0.4.0 is via
  `--permission-mode`, **not** an answer-injection path (§5); the auto-answer
  engine that would consume `BlockedReason` is deferred (§14).
- **Zero git handling anywhere** (`grep git` / `exec.Command("git"` → nothing).
  Worktrees start from a new helper package (§6).
- **Golden corpus ready**: `testdata/golden/streamjson/` — 5 real transcripts
  (simple-text, bash tool-use, write/read tool-use, resumed-session,
  permission-denial), claude 2.1.224, **no consumer yet**. `result` line fields
  documented (spike-notes.md:49-52): `is_error, total_cost_usd, usage,
  permission_denials[], num_turns, duration_ms, stop_reason`; denials join via
  `tool_use_id`. On-disk ≠ stdout: deltas and `system` events never persist;
  one `assistant` record per completed content block (spike-notes.md:53-54).
- **fakeclaude** (`test/fakeclaude/main.go:59-66`) recognizes only interactive
  flags. Teaching it `-p`/`--output-format`/`--input-format` is an explicit M4
  sub-task (RUNBOOK:216).
- **CLI** is a flat map (`cmd/corral/main.go:29-41`). M4 adds `run`, `review`
  (both visible), following `cmd_new.go`/`cmd_answer.go`.

**Absent — M4 adds:** `internal/claude/streamjson/` (parser), headless spawn
fork (pipe capture), `internal/orchestrator/` (task DAG), a git-worktree helper,
`tasks`/`task_deps`/cost columns (migration `0004`), `corral run`,
`corral review`, and `fakeclaude` headless mode.

## 3. Task/DAG model + store (migration 0004)

### 3.1 A task *owns* sessions (decision, advisor-reviewed)

A **task** is one unit of orchestrated work — a prompt run in a repo/worktree
to completion. A **session** is one headless `claude` invocation. **A task owns
0..N sessions** (one per attempt); it is not itself a session.

Why not fold task state into `sessions`:

- **Cardinality.** A retried task produces multiple sessions. One row cannot
  hold N attempts' `claude_session_id`s, exit states, or costs.
- **The partial unique index bites.** `sessions_name_active` forbids two
  non-terminal rows sharing a `name`. On the *first backoff retry* of a task
  folded into `sessions`, attempt #2 collides with attempt #1's name until #1
  goes terminal. Separating the models sidesteps this; the task assigns each
  attempt a **distinct** session name `<task-name>-a<N>` and only starts attempt
  N+1 after attempt N's row is terminal (`exited`/`failed`) — belt and
  suspenders.

`tasks.session_id` (nullable) points at the **current attempt's** session.
History lives in events + the terminal session rows.

### 3.2 Schema (`0004_tasks.sql`)

```sql
CREATE TABLE tasks (
  id            TEXT PRIMARY KEY,          -- uuid
  dag_id        TEXT NOT NULL,             -- groups a run; a single `corral run` w/o deps is a 1-node dag
  name          TEXT NOT NULL,             -- human label; session names derive as <name>-a<attempt>
  prompt        TEXT NOT NULL,             -- corral OWNS the prompt (drives spawn + re-send, §9)
  repo          TEXT NOT NULL,             -- absolute repo path
  cwd           TEXT NOT NULL,             -- worktree path once created, else repo
  worktree      TEXT,                      -- worktree path if --worktree, else NULL (runs in repo)
  branch        TEXT,                      -- branch-per-task name if worktree, else NULL
  model         TEXT,                      -- per-task model declaration (not routing, §14)
  permission_mode TEXT,                    -- resolved user/env-only; NULL => daemon default
  status        TEXT NOT NULL,             -- pending|ready|running|succeeded|failed|cancelled|blocked
  attempts      INTEGER NOT NULL DEFAULT 0,
  max_attempts  INTEGER NOT NULL DEFAULT 1,
  session_id    TEXT,                      -- current attempt's session (FK sessions.id, ON DELETE SET NULL)
  cost_usd      REAL NOT NULL DEFAULT 0,   -- rolled up across this task's attempts
  budget_usd    REAL,                      -- per-task cap; NULL => unbounded (dag budget still applies)
  created_ms    INTEGER NOT NULL,
  updated_ms    INTEGER NOT NULL,
  FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE SET NULL
);
CREATE INDEX tasks_dag ON tasks(dag_id);

CREATE TABLE task_deps (
  task_id   TEXT NOT NULL,                 -- the dependent
  depends_on TEXT NOT NULL,                -- must reach succeeded first
  PRIMARY KEY (task_id, depends_on),
  FOREIGN KEY (task_id)   REFERENCES tasks(id) ON DELETE CASCADE,
  FOREIGN KEY (depends_on) REFERENCES tasks(id) ON DELETE CASCADE
);

CREATE TABLE dag_budgets (
  dag_id     TEXT PRIMARY KEY,
  budget_usd REAL,                          -- NULL => unbounded
  cost_usd   REAL NOT NULL DEFAULT 0        -- rolled up across all tasks in the dag
);
```

**Sharp edges:**
- Migration connection opens `foreign_keys(OFF)` (migrate.go precedent);
  long-lived conn is `foreign_keys(ON)`. FKs above are enforced at runtime.
- `status` is a string enum mirroring the `session.Status` convention (no CHECK
  constraint — validate in Go, matching existing tables).
- Cost is stored **twice** (task + dag rollup) and updated in one transaction
  per turn (§7). Denormalized on purpose: `corral ls --cost` must not re-sum
  events on every render.

### 3.3 Store surface (`tasks.go`)

`CreateTask`, `GetTask`, `ListTasks(dagID)`, `UpdateTask(id, mutate func)`
(mirrors `UpdateSession`), `AddDep`, `ReadyTasks(dagID)` (tasks whose deps are
all `succeeded`), `AddCost(taskID, usd)` (task + dag rollup, one tx),
`SetTaskSession(taskID, sessionID)`, `RunningTasks()` (all tasks
`status='running'` across dags — orchestrator daemon-start reconciliation, §9).

**`CreateDAGBudget(dagID, budgetUSD *float64)`** inserts the `dag_budgets` row
(one per `dag_id`, `cost_usd=0`). This is the **sole writer of the row itself** —
`AddCost` only *updates* the rollup and assumes the row exists. `corral run`
submission (a whole dag, atomic) calls `CreateDAGBudget` once before inserting
its tasks (§13 step 24). No dag ever has tasks without its budget row.

## 4. stream-json parser (`internal/claude/streamjson`) — authored FIRST

Authored before the spawn path: it eats bytes from anywhere, the golden corpus
is a complete contract, and a proven parser de-risks §5's integration.

### 4.1 Protocol shape (from spike-notes.md + golden corpus)

Each stdout line is one JSON object with a `type`. v0.4.0 handles:
- `system` — **many subtypes, not just `init`** (real corpus: `init`,
  `hook_started`, `hook_response`, `thinking_tokens`, `permission_denied`).
  `init` carries `session_id`, `tools`, `model`. **Do not assume a fixed
  `tools` list** (local hook/MCP noise — spike-notes.md:65-67). Non-`init`
  subtypes pass through untyped.
- `assistant` — one per completed content block; `message.content[]` holds
  `text` and `tool_use` blocks. (`subtype` is JSON `null`, not absent, on
  assistant/user lines — a `string` field handles it; do not switch to
  `*string` expecting omission.)
- `user` — `tool_result` blocks (join to `tool_use` via `tool_use_id`). A
  tool_result may carry its own `is_error:true` (a failed tool call) — this is
  **not** the terminal result's `is_error` (see below).
- `result` — terminal: `is_error, total_cost_usd, usage{input/output/cache_*},
  permission_denials[] (each also carries tool_input, dropped in v0.4.0),
  num_turns, duration_ms, stop_reason, session_id`. Real result lines carry many
  more fields (`modelUsage`, `terminal_reason`, `ttft_ms`, `api_error_status`,
  …) — all tolerated/dropped by the plain-struct decode.
- `rate_limit_event` — a **top-level type**, not a `system` subtype (5 in the
  corpus). Passes through untyped; harmless.
- `--include-partial-messages` deltas — **recognized and skipped** in v0.4.0
  (streaming UI is not on the exit-criterion path). Log-and-ignore unknown
  types; never error on them.

**Corpus gap (flagged for §8.1):** every golden `result` line is
`is_error==false / subtype=="success"`. The result-line **failure** branch
(`is_error==true`) is uncovered by real data — fakeclaude's `error-turn`
scenario (§12) must *synthesize* it so the orchestrator's failure mapping is
exercised. (The one `is_error:true` in the corpus is a nested tool_result, not a
terminal result.)

### 4.2 API

```go
type Event struct {
    Type    string          // system|assistant|user|result|<unknown>
    Subtype string          // init, etc.
    Raw     json.RawMessage // full line, for the tee/audit
    // decoded convenience fields, populated per-type:
    SessionID string
    Result    *Result       // non-nil only on type==result
    ToolUses  []ToolUse     // on assistant
    Text      string        // concatenated text blocks on assistant
}
type Result struct {
    IsError      bool
    TotalCostUSD float64
    Usage        Usage
    Denials      []Denial   // tool_use_id + tool_name
    StopReason   string
    NumTurns     int
}
// ParseLine decodes ONE line. Unknown type => Event{Type:...} with nil Result,
// never an error. Malformed JSON => error (caller logs + continues).
func ParseLine(b []byte) (Event, error)
```

### 4.3 Versioning + fuzz

- Parser is tolerant-by-default (unknown fields ignored via plain struct decode;
  unknown types pass through). This absorbs claude-CLI version drift without a
  hard version gate — the golden corpus is the regression net; a new capture at
  a new CLI version is added, never a schema bump.
- `FuzzParseLine` (RUNBOOK §5.3) — corpus seeded from every golden line.
  Invariant: `ParseLine` never panics; on `type==result` with `is_error=false`,
  `TotalCostUSD >= 0`.

## 5. Headless spawn path (the PTY-vs-pipe fork)

### 5.1 BuildArgv

`BuildArgv` gains a `Mode==ModeHeadless` branch appending, after the existing
identity/settings flags:

```
-p "<task.prompt>"        (prompt as ARGV — one-shot invocation)
--output-format stream-json
--verbose                 (stream-json requires it for full records)
--permission-mode <mode>     (§5.3)
```

`-p "<prompt>"` is a **one-shot** invocation (M0 spike V3, `main.go:345`: prompt
passed as argv, child runs it, emits `result`, exits ~880ms after signal — no
persistent stdin loop was ever kept alive). v0.4.0 therefore carries **no
`--input-format stream-json`**: there is no live process to inject frames into.
Re-send (§9) is a *fresh* `--resume -p "<prompt>"` invocation, not frame
injection. `--input-format stream-json` (multi-turn injected input into a live
child) is deferred (§14).

No `--include-partial-messages` in v0.4.0 (we skip deltas — §4.1; adding it only
increases stdout volume for records we drop).

**Persisted argv redaction (decided).** `Registry.Spawn` persists
`sess.Argv = BuildArgv(spec)`, so the headless branch would land the full prompt
text in the `sessions.argv` column. The prompt is **user-authored** (it comes
from `corral run` / `dag.toml`, and corral already owns `task.prompt` in
cleartext per §3.2), so persisting it is not the agent-content leak the standing
"redact agent content before persisting" rule guards against. But it is
needless duplication and column bloat. Decision: `BuildArgv(spec, redact bool)`.
The **exec** copy (`redact=false`) carries the real `-p "<prompt>"`; the
**persisted** copy (`redact=true`) replaces the prompt value with a placeholder
`-p "<prompt:NNN bytes>"`. Interactive spawn has no prompt, so `redact` is a
no-op there. Two call sites in `Spawn`: exec builds with `false`, the persist
write with `true`.

### 5.2 The fork (`spawn_headless.go`)

`Spawn` dispatches on `Spec.Mode`:
- `ModeInteractive` → existing `pty.StartWithSize` path (untouched).
- `ModeHeadless` → `cmd.StdoutPipe()` + `cmd.StderrPipe()`, `Setsid:true`
  (PGID==PID, same process-group discipline so SIGTERM-to-group and the M3
  checkpoint/reaper machinery work identically). **stderr is not clean**
  (spike-notes.md:59 — warnings) → parse **stdout only**; tee stderr to a capped
  diagnostic log.
- **Reader goroutine (A)** consumes stdout. **It MUST use
  `bufio.Reader.ReadBytes('\n')` in a loop — NOT `bufio.Scanner`.** A
  `system:init` line with a large `tools` array, or an `assistant` line with a
  big `tool_use` input, routinely exceeds Scanner's 64KB `MaxScanTokenSize`;
  Scanner then returns `bufio.ErrTooLong` and **stops**, silently truncating the
  rest of the session's stream — *including the terminal `result` line*. That is
  a lost-`result` failure (→ §8.1 rule 3, spurious "mid-turn-crash"), not a test
  failure, so it hides under load. `ReadBytes('\n')` has no line cap. The final
  chunk before EOF may be a partial line (child killed mid-line): decide it
  explicitly — parse it if it is valid JSON, drop it otherwise; never treat a
  partial as the loop's error exit. Blank lines are **skipped** (`ParseLine("")`
  errors by design — a line with no `type` cannot be classified). Each parsed
  line → (a) tees `Raw`+`\n` to a structured stream log — the authoritative
  in-flight record (§9), and the full record of tool_use/denial lines (no
  separate per-tool event kinds in v0.4.0; the stream log holds them), (b) on
  `result`, stashes the parsed `Result` on the `LiveSession` and emits the one
  new durable event kind, `session.result` (carrying `is_error`/
  `total_cost_usd`/`stop_reason`/`num_turns`; its `permission_denials` summary
  is the denial record) — §8.1. **The reader does NOT call `AddCost`** — cost
  rollup is the orchestrator's, driven by the event (§7, §8.1); the supervisor
  stays free of the tasks/cost packages (no import cycle).
- **stderr goroutine (B)** drains the stderr pipe to a capped diagnostic log. It
  MUST drain to EOF even if the log is capped — a full, unread stderr pipe
  blocks the child.
- **Reaper goroutine (C)** — ordering is the **inverse of the PTY path** and is
  load-bearing. `cmd.Wait()` closes the pipes returned by `StdoutPipe()`/
  `StderrPipe()` when it returns, so calling `Wait()` while A/B are still reading
  is a documented data race that can drop the tail of the stream — again the
  `result` line. Order: **wait for A and B to reach EOF → *then* `cmd.Wait()` →
  then deregister + reap.** (The PTY path does the opposite: `Wait()` first, then
  closing the master unblocks the reader. Do not copy that order here.) `reap`
  applies the §8.1 attempt-outcome rule to the stashed `Result` (or its absence).
- The child **exits at `result`** (one-shot): terminal state is the process exit,
  not an idle timeout.

**This is the only new spawn mechanism, but it is a genuine fork, not a
drop-in.** The plumbing downstream of *how* the child is read — PGID, secret,
env whitelist, `Checkpoint`, `Wake` — is unchanged. But the read itself forks:
headless `LiveSession` carries **no `PTYMaster` and no `Screen`** (both nil),
`WriteInput` on a headless session is an **error** (one-shot, no input channel),
and `runGoroutines` forks so goroutine A above replaces the PTY-reader→`Screen.
Feed` loop. A second exception is `Recover`: it must skip headless task-owned
sessions, which the orchestrator reclaims instead (§9).

### 5.3 `--permission-mode` — security boundary

Closing the latent gap. For unattended runs the task declares its permission
posture; v0.4.0 has **no answer-injection**, so a blocking prompt would hang the
task (the orchestrator's per-task timeout reaps it — §8). Practical postures:
`default` (blocks on risky ops — a task that hits one fails on timeout, which is
*safe*), `acceptEdits`, `plan`. `bypassPermissions` is **reachable from config
for the first time** via this path.

**Rule (enforced, doc-stated like m3.md's `idle_timeout`):**
`session.permission_mode` (and any task-level override) is **user-file/env-only
— never repo-settable**, already the case in `repo_allowlist.go`. A cloned repo
must not be able to set its own tasks to `bypassPermissions`. The task-level
`permission_mode` resolves through the same user/env pipeline; a repo
`.corral.toml` value is dropped + reported as a `Rejection`. When the
(deferred) auto-answer allowlists land, they sit on this same side of the
boundary.

## 6. Worktree isolation (`internal/git`)

Greenfield — no git code exists.

### 6.1 Helper surface

```go
func AddWorktree(ctx, repo, path, branch string) error   // git -C repo worktree add -b branch path HEAD
func RemoveWorktree(ctx, repo, path string) error         // git -C repo worktree remove --force path
func ListWorktrees(ctx, repo string) ([]Worktree, error)  // porcelain parse
```

- **Branch-per-task**: `corral/task/<task-name>-a<attempt>`. Isolation is the
  point — two tasks touching the same repo never share a working tree or branch.
- **git invoked via `exec.CommandContext`, never a shell** — args as a slice
  (matches the `corral answer` no-shell-interpolation rule). Paths are
  daemon-constructed, never repo-file-derived.
- **Lifecycle**: worktree created when the task transitions `ready→running`;
  removed when the task reaches a terminal state **and** the review gate has
  released it (§10) — a *failed* task's worktree is **retained** for inspection
  (removal only on success-after-review or explicit `corral review --discard`).
  Cleanup is best-effort + logged; a leaked worktree never blocks the DAG.
- **Collision**: `AddWorktree` fails if `path`/`branch` exists → the task fails
  its attempt (retry derives a new `-a<N>` branch, so no infinite collision).

### 6.2 Worktree intent + per-attempt resolution (step 21)

Resolved during step-21 grounding (advisor). The schema (`tasks.worktree
TEXT NULL`, "worktree path if `--worktree`, else NULL — runs in repo") is the
intent signal; **no boolean column, no migration**:

- **Intent = non-empty `Worktree` at submission.** Step 24's submission writes
  a placeholder base dir (`<state_dir>/worktrees/<dag>/<task>`) when
  `--worktree` is given, and leaves it `""` otherwise.
- **Per-attempt resolution is the orchestrator's job.** On each attempt the
  orchestrator computes `path = <state_dir>/worktrees/<dag>/<name>-a<N>`,
  `branch = corral/task/<name>-a<N>`, calls `AddWorktree(repo, path, branch)`
  (**always from `HEAD`** — no `startPoint` param), overwrites the row via
  `UpdateTask{Worktree: path, Branch: branch}`, and runs the child with
  `cwd = path`. Empty `Worktree` → `cwd = task.Repo`, no worktree, no branch.

- **Cross-node work does NOT flow through branch inheritance.** corral never
  commits or merges (§10) — the implement node leaves its edits **uncommitted**
  in its worktree, so a dependent node branching from the dependency's branch
  (or given its branch name) would see nothing. Instead the orchestrator
  **injects each running task's resolved dependency worktrees into the child
  environment** as `CORRAL_DEP_WORKTREES`, a JSON array
  `[{"name","worktree","branch"}]` (JSON, not `:`-joined — a macOS path may
  contain `:`; and a consumer wants the dep *name*, not just its path). A
  review node's claude reads/diffs the implement node's live worktree directly.
  - This env var is corral-owned: it is added **inside `BuildEnv`** from a new
    `Spec.DepWorktrees` field (pre-marshaled JSON string), exactly the way
    `CORRAL_SESSION_ID`/`CORRAL_SOCK` are added — **never** stuffed into
    `spec.Env` after `BuildEnv` returns. `BuildEnv`'s invariant ("the returned
    map is always exactly … nothing else, regardless of what snapshot
    contains") guards a real past leak (finding #3, `CLAUDE_CODE_CHILD_SESSION`)
    and must stay true; sourcing from `snapshot` is forbidden.
  - **Scope fence:** step 21 ends at "the dependency worktree paths reach the
    child, asserted by test." *What the review node does with them* — the
    prompt preamble, any `dag.toml` review template — is step 24's
    prompt-authoring problem. An agent handed both will conflate them.

### 6.2 Where worktrees live

Two distinct locations, do not conflate them:
- **The checkout** lives at `<state_dir>/worktrees/<dag>/<task>-a<N>` — a
  daemon-owned dir, passed as the `path` arg to `git worktree add`. This keeps
  the repo tree clean and cleanup contained (git worktrees may live outside the
  repo dir).
- **git's own bookkeeping** for that worktree lands in `<repo>/.git/worktrees/`
  where git puts it — git-internal, **corral never reads or writes it**.
  Removal goes through `git worktree remove`, never `rm -rf` of either path.

## 7. Cost accounting

- The `result` line's `total_cost_usd` is the **authoritative per-invocation
  cost** (spike-notes.md:50). On each parsed `result`, the runner calls
  `AddCost(taskID, total_cost_usd)` — one transaction updating `tasks.cost_usd`
  **and** `dag_budgets.cost_usd`.
- **Budget stop-at-limit (post-hoc + gate-next, decided step 22).** The
  governing invariant: **budget never rewrites the outcome of a turn that
  already happened; it only forbids future spend.** A headless child has
  already exited by the time its `result` is observed (§5.1 one-shot) — there is
  nothing to signal or checkpoint, so the old "SIGTERM-to-group / mark the
  producing attempt `failed`" phrasing was doubly wrong (headless is exempt from
  the checkpointer per §8.2, and `failed`-ing a completed attempt discards paid
  work *and* lies to `ReadyTasks`, which keys dependent readiness on
  `dep.status = 'succeeded'`). Concretely:
  - `est = 0`. There is no cost estimator anywhere; enforcement is purely
    post-hoc — gate only when `cost_usd` is **already** at/over budget. A dag or
    task with **no budget row** or `budget_usd IS NULL` is **unbounded — never
    gated** (`CreateDAGBudget` is step 24's job, so today no dag has a row; a
    backwards default here would stop the orchestrator entirely and break the
    step-21 suite).
  - Budget forbids exactly two future-spend paths, both gated in `launchReady`
    only (`pollInFlight`/`enforceTimeouts` stay **ungated** — outcomes are still
    harvested and hung children still killed in an over-budget dag; that *is*
    "in-flight siblings finish their current turn"): **(a)** starting a new
    ready task, and **(b)** retrying a failed attempt. Path (b) is enforced by
    passing an `overBudget bool` into `applyOutcome` — the single terminal-
    disposition site (same "no second mapping" discipline as `HeadlessOutcome`):
    when over budget, a would-be retry becomes terminal instead of scheduling
    `nextAttemptAt`. A **successful** over-budget attempt stays `succeeded`.
  - **Recording the trip:** `status` stays `failed` (no CHECK constraint on
    `tasks.status`, but `failed` is already terminal in every consumer —
    `terminalDAGStatuses`, `ReadyTasks` — so no new value to re-audit; no
    migration). The reason is a durable event
    `EventTaskBudgetExceeded` attached to the tripping attempt's `session_id`
    with `{task_id, dag_id, cost_usd, budget_usd}`, tying the record to the
    exact attempt that crossed the line.
  - **No perpetual stall:** an over-budget dag's remaining `pending`/`ready`
    tasks are marked `cancelled` (already terminal, already in
    `terminalDAGStatuses`) the tick the budget trips; `running` ones finish and
    record normally. The dag reaches a clean terminal state once the last
    in-flight attempt lands — giving step 24's `corral run` a termination
    condition instead of a dag `ActiveDAGs` returns forever.
  - **Known under-count (not a code change):** `AddCost` runs only when a
    `result` was captured, so a mid-turn crash (§8.1 rule 3) records **no**
    cost even though it spent real money — there is no cost figure to record.
    The recovery **harvest** path (§9) shares this under-count: `total_cost_usd`
    lives only in the stream-json `result` line (lost with the pipe on the
    crash), never in claude's own conversation transcript, so a harvested
    orphan is marked `succeeded` with **no cost recorded**. Budget enforcement
    is therefore a lower bound on true spend.
- `corral ls --cost` reads the denormalized rollups — **deferred to step 24**:
  no dag/task is creatable via any interface until step 24's `corral run`, so
  there is no data source to render or test against in step 22. `corral run`
  prints the dag total on completion (also step 24).

## 8. Orchestrator (`internal/orchestrator`)

### 8.1 Execution

- `dag.go`: build graph from `task_deps`, **detect cycles** (reject at
  `corral run` submission, before any spawn), compute the ready-set (tasks whose
  deps are all `succeeded`).
- `run.go`: a loop that, while the dag is not done and not over budget: starts
  every ready task not already running (spawns a headless session via the
  supervisor, sets `tasks.session_id`), waits for any running task's session to
  reach a terminal state, maps session outcome → task outcome, recomputes the
  ready-set. Concurrency within a dag is natural (independent branches run in
  parallel); v0.4.0 caps concurrent tasks at a small constant (config,
  default 4) to bound machine load.
- **Retry/backoff**: on a task attempt failure that is *retryable* (session
  `failed`/timeout, not over-budget (§7's `overBudget` gate), not a cycle), if `attempts <
  max_attempts`, re-enqueue with exponential backoff (base 2s, cap 60s, via the
  injected `clock.Clock` so tests are deterministic). Each retry is a fresh
  session `<name>-a<N>` in a fresh worktree branch.

- **Attempt-outcome authority (one rule, decided).** A headless attempt has two
  signals that can disagree: the parsed terminal `result` line
  (`is_error`/`stop_reason`) and the process exit code. **The captured `result`
  is authoritative; the exit code is only a fallback when no `result` was
  captured.** Concretely, the supervisor's headless reap maps:
  1. `result` captured with `is_error==false` ⇒ **success**, regardless of exit
     code (a nonzero exit after a clean result does not un-succeed the turn).
  2. `result` captured with `is_error==true` ⇒ **failure** (retryable — the
     `error-turn` shape; corpus-gap branch, see §4.1 / §12).
  3. **no `result` captured** (child killed by SIGTERM/timeout, crashed
     mid-turn, or pipe closed before the terminal line) ⇒ **failure**,
     regardless of exit code. This is the `mid-turn-crash` case §9 hands to the
     retry path.
  The reaper stashes the parsed `Result` on the `LiveSession` and emits a
  durable `session.result` event (`is_error`/`total_cost_usd`/`stop_reason`/
  `num_turns`); the orchestrator reads that terminal state to apply this rule
  and (step 22) to call `AddCost`. Step 19 wires the capture + event; step 21
  consumes it. Do **not** invent a second mapping in `run.go`.
  - **nil vs present-and-false (highest-severity trap in step 21).** Rule 3
    hinges on the orchestrator distinguishing *no `session.result` event
    found* from *a result with `is_error==false`*. The "no result" path MUST
    yield a `nil *streamjson.Result` reaching `HeadlessOutcome`, **never**
    `&Result{IsError:false}` — the latter silently converts every mid-turn
    crash into a success, the single worst bug available here, and no other
    step-21 test would catch it. **Required test:** a headless session that
    exits with no `session.result` event must end the task `failed`, not
    `succeeded`.

### 8.2 Reaper interaction (advisor gap — decided)

**Headless sessions are exempt from the idle reaper.** The M3 reaper
(`reaper.go`) targets human-abandoned interactive TUIs: its activity signal is
`WriteInput`/attach/hook (m3.md §2.1), none of which a headless task emits, so a
40-minute headless task would look "idle" and get checkpointed mid-DAG-node.
`reaper.go` gains one predicate: skip `Mode==ModeHeadless`. The **orchestrator
owns headless lifecycle** — its own per-task timeout (config
`orchestrator.task_timeout`, default 30m) checkpoints a genuinely stuck task,
and budget enforcement (§7) handles cost runaway.

*(Alternative considered: have the stream-json runner call `TouchActivity` on
each parsed turn, keeping headless in the reap set. Rejected — it couples two
independent lifecycle owners and makes a task's reap-safety depend on turn
cadence. Exemption is cleaner and the orchestrator already has timeout
authority.)*

**Side-door caveat (keep `settings.Pin`, know why).** Headless spawn keeps the
M1 shared prologue including `settings.Pin`, so a headless child *does* install
the hooks relay and *will* call back the hook endpoint with its session secret
(authenticated, harmless). That means headless children emit hook activity — the
very signal the reaper keys on. Today that is inert because the predicate above
skips `Mode==ModeHeadless` *before* consulting activity. The hazard is future:
anyone who removes the exemption thinking "hooks give headless activity now"
silently re-couples the two lifecycle owners this section rejected. **The reaper
exemption predicate (step 21) must carry an inline comment**: hook-derived
activity from headless children is deliberately NOT a reap signal — the
exemption is by mode, not by silence.

**Config is a trust boundary (advisor — decided; scope refined).**
`task_timeout` (30m) and `max_concurrent` (4) are lifecycle authority: the
reaper exempts headless (§8.2), so `task_timeout` is the *only* thing that
checkpoints a stuck headless child, and `max_concurrent` gates fork-bomb
pressure. A repo `.corral.toml` MUST NEVER be able to set either.

In v0.4.0 (step 21) these are **not TOML-exposed at all** — they are fields on
an `orchestrator.Config` struct injected at construction with daemon-supplied
defaults, exactly the way `reaper.New` takes `idleTimeout` as a plain arg. "Not
repo-settable" is thus satisfied by construction: there is no `.corral.toml` key
to attack. **When** a later step exposes them as `[orchestrator]` TOML, that
step MUST add both to `config/repo_allowlist.go`'s reject list following the
`state.idle_timeout` precedent — recorded here so the requirement isn't lost.

## 9. Re-send for headless (M3 §5.2 deferral — now tractable)

M3 deferred re-send because interactive PTY has no corral-owned prompt record.
Headless removes that blocker: **`task.prompt` is corral-owned**, so re-send
needs no disk archaeology.

**Re-send is a fresh one-shot, not frame injection.** Because `-p` exits at
`result` (§5.1), there is no live child to write a frame into on recovery.
"Re-send" = start attempt N+1 the ordinary way: a **fresh** session
(`--session-id`, not `--resume`) in a **fresh** worktree, re-supplying
`task.prompt`. It reuses the retry machinery (§3.1/§8.1) with no new plumbing.

**Why fresh, not `--resume` (advisor — decided step 23).** `--resume
<claude_session_id>` would hand the re-spawned child the previous attempt's
conversation transcript — a transcript that claims edits the child made. But
§6.2 pins **one fresh worktree per attempt** (`<name>-a<N>`, always
`AddWorktree` from HEAD), so the re-spawned attempt's filesystem is reset to
HEAD: the resumed transcript would reference edits that do not exist on disk,
which is *worse* than starting cold. `--resume` is coherent only if the
respawn **reuses** the orphan's worktree; that reuse breaks §6.2's
own-fresh-worktree invariant and can inherit a half-applied edit, so it is
**deferred**. v0.4.0 respawn is a plain fresh retry — which is exactly what the
step-21 reconciler already does (`applyOutcome(false)` → `TaskPending` →
`launchReady` spawns a fresh attempt). No `spec.ResumeFrom` threading is added.

**The daemon-restart hole (advisor gap — decided).** M3's `Recover` relaunches
every `desired_state='running'` row via `--resume` on daemon start. For a
headless task session this is *wrong*: the orchestrator loop that owned it
(§8.2) no longer exists after a restart, so a blind `Recover` relaunch would
leave a resumed child with no timeout authority and a `tasks.status='running'`
row that never advances. Decision, split by owner:

- **`Recover` skips headless task-owned sessions** (`Mode==ModeHeadless`) —
  it does not relaunch them. It owns only interactive TUIs.
- **The orchestrator rebuilds its in-flight set from `tasks WHERE
  status='running'` on daemon start** and drives each through recovery: the
  original child was detached (own `Setsid` pgroup) and may have kept running,
  but its stdout pipe died with the parent, so its `result` is unrecoverable.
  The orchestrator treats the orphaned attempt as failed, then applies the
  transcript check below to decide whether the *work* completed before
  re-spawning.

**Recovery decision (per orphaned/mid-turn task):**
- Inspect the transcript via `LastRecordIsCompletedTurn`. If the last turn **is**
  a completed assistant turn (`stop_reason=="end_turn"`), the work landed even
  though corral lost the pipe — mark the task `succeeded`
  (`applyOutcome(success=true)`), do **not** re-spawn (no double-run). No cost is
  harvested: `total_cost_usd` was in the lost `result` line, not the transcript
  (§7 under-count).
- If the last turn is **not** complete (mid-turn crash, the flush-lag case from
  spike finding #1), fail the orphaned attempt → normal retry (fresh worktree,
  fresh session; **not** `--resume`, per the decision above).
- The tee'd stream log (§5.2) is the in-flight record; transcript = flush-verified;
  `task.prompt` = what to re-send. All three exist for headless.
- v0.4.0 scope: re-spawn at most **once** per recovery. Beyond the transcript
  check, this is best-effort recovery, not exactly-once.

**Step 21 / step 23 seam (advisor — decided).** The transcript-check
(`LastRecordIsCompletedTurn` harvest) belongs to step 23, not step 21. To keep
the boundary a *replacement* rather than a rewrite, step 21 implements
reconciliation through a single classifier:

```go
func classifyOrphan(task) orphanAction   // returns harvest | respawn
```

Step 21's implementation **always returns `respawn`** (fail the orphaned
attempt → normal retry). Step 23 replaces *only* this classifier body with the
transcript check (return `harvest` when the last turn is a completed
`end_turn`). Critically, step 21 must **not** mark the orphan `failed` and
re-spawn in the same pass such that a second child exists before the classifier
runs — the harvest path in step 23 needs to see the orphan *before* any respawn.
Reconciliation is therefore two-phase: classify all orphans first, then act.

**Step 23 classifier mechanics (decided).** `classifyOrphan` resolves the
transcript with no new interface seam: `Store.GetSession(task.SessionID)`
(already in the orchestrator's `Store` interface) yields the session's
`ClaudeSessionID` and `Cwd`; `sessions.TranscriptPath(claudeHome, cwd,
claudeSessionID)` builds the path; `checkpoint.LastRecordIsCompletedTurn` reads
it. `claudeHome` is injected as a plain `orchestrator.Config.ClaudeHome` field
at daemon construction (config-trust-boundary posture per §8.2 — not
TOML-exposed). `orchestrator` importing `checkpoint`/`claude/sessions` forms no
cycle (neither imports `orchestrator`).

**Err toward `respawn`, always (load-bearing — nil-trap severity class).** A
wrong `harvest` marks unfinished work `succeeded` and releases its dependents on
a lie; a wrong `respawn` merely re-runs completed work. So `classifyOrphan`
returns `orphanRespawn` on *every* uncertainty: `GetSession` error, empty
`ClaudeSessionID`, missing/unreadable transcript, or `LastRecordIsCompletedTurn`
error (which already errs toward `false`). `harvest` requires a positive
completed-`end_turn` verdict and nothing less.

## 10. Review gate (`corral review`)

The moat: **corral never merges or pushes.** A completed task leaves its work on
its worktree branch. `corral review [<dag>]`:
- lists each terminal task, its branch, and a `git -C <worktree> diff` summary
  (stat + optional full diff), read-only.
- offers **no** merge/push/rebase verb in v0.4.0. Releasing a worktree
  (`corral review --release <task>` removes a *succeeded* task's worktree;
  `--discard` removes a failed one) is the only mutation, and it only touches
  corral-owned worktrees, never the user's branches.
- Human runs `git merge`/`git push` themselves. This is the explicit "nothing
  merges without human action" contract (RUNBOOK).
