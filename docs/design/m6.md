# corral M6 design — learning loop (hermes)

**Status:** in progress. **Target:** `v0.6.0`.

**Milestone goal (RUNBOOK.md §M6):** turn corral's supervised-session history
into durable, repo-scoped improvements through a closed loop: mine evidence,
verify a candidate, present an inspectable proposal, require explicit adoption,
then measure the result and flag regressions or stale artifacts.

**Exit criterion (RUNBOOK.md §M6):** on a dogfooded repository over two real
14-day windows, reduce blocked events and cost relative to the preceding
window, with zero unapproved repository writes.

M6 is deliberately narrower than the full five-artifact vision in the
RUNBOOK. `v0.6.0` closes the complete loop for the first attack-order item,
**permission-rule suggestions**. Operational memory, model routing, skill
synthesis, and the failure regression corpus build on the same artifact,
evidence, verification, adoption, and measurement substrate, but are deferred
to §15. Shipping one trustworthy closed loop is more valuable than five
candidate generators with no trustworthy feedback path.

---

## 0. Grounding in the current tree

M5 closed at step 35 / tag `v0.5.0`. The relevant existing seams are:

- `events` is append-only and every persisted timestamp comes from the injected
  `clock.Clock` (`internal/store/events.go`). Events are the authoritative
  evidence source; learning rows are materialized projections, never a
  replacement history.
- `permission.requested`, `permission.blocked`, `permission.resolved`, and
  `session.answered` already describe the permission lifecycle. However,
  `permission.requested` currently persists only `prompt_id` and `tool_name`;
  it does **not** retain the command/tool input needed to propose a rule.
- `state.BlockedReason` carries the exact open permission's `HookSeq` and tool
  input while blocked. Both HTTP answer and ntfy reply read the current session
  row before writing input, so they can stamp that `HookSeq` into the existing
  `session.answered` audit event without changing answer semantics.
- The session's pinned settings file is generated by
  `internal/claude/settings.BuildSettingsJSON` and passed via `--settings`.
  This is the safe adoption point: an adopted permission rule can be merged
  into the next generated pinned file. No repo file needs to be written.
- Claude Code's current official permission contract (verified 2026-08-09 at
  <https://code.claude.com/docs/en/permissions>) uses
  `permissions.allow: ["Tool(specifier)"]`; deny and ask rules take precedence
  over allow rules, and Bash compound commands are checked per subcommand.
  M6 never tries to outsmart or replace that evaluator.
- The daemon already has a non-blocking SSE invalidation channel and a secured
  dashboard. Learning changes use the same append-event → broker path.
- The store schema is at migration 0005. M6 starts with 0006.

### Load-bearing constraints

1. **No unapproved writes.** Mining, verification, and proposal are DB-only.
   Adoption requires an explicit authenticated CLI/API/dashboard action. Even
   after adoption, v0.6.0 writes only corral's state directory and future
   per-session pinned settings; it does not edit `.claude/settings*.json`,
   `CLAUDE*.md`, `.corral.toml`, or any user repository file.
2. **Default deny.** A candidate is never active merely because it was mined
   or verified. Only `status=adopted` affects a spawned session.
3. **No secret retention.** Tool input is redacted before it reaches the
   append-only log, capped with the same configured event-payload limit, and a
   redacted/truncated input is ineligible for synthesis. Step 37 also applies
   the same redaction to the persisted `BlockedReason`; its current raw
   `tool_input` persistence is an inherited gap that M6 must close.
4. **Human approval must be proven.** A `PostToolUse` outcome of `approved`
   alone is insufficient because Auto Mode can approve without the operator.
   Policy evidence requires a correlated `session.answered` for the exact
   blocked request followed by `permission.resolved outcome=approved`.
5. **Evidence is immutable and attributable.** Every learning points to the
   source event sequence numbers that taught it. State transitions append a
   `learning.*` event carrying learning ID + repo, never opaque prose alone.
6. **Verification precedes proposal.** Unverified candidates do not appear in
   the normal proposal list and cannot be adopted.
7. **No silent positive conclusions.** Measurement always includes numerator,
   denominator, window, and sample sufficiency. Too little data is
   `inconclusive`, never "improved".
8. **No LLM on the permission-rule path.** Exact repeated approvals have a
   deterministic synthesis. Adding a model would add cost and nondeterminism
   without improving ground truth. Later free-form artifact kinds introduce a
   narrow structured synthesizer interface (§15).

## 1. v0.6.0 product slice

An operator sees:

> You approved `npm test` 6 times in `/repo` during the last 14 days.
> Candidate: `Bash(npm test)`. Estimated avoidable blocks: 6.

They can inspect the evidence and the exact pinned-settings diff, then adopt or
reject it. Adoption affects only newly spawned/resumed sessions for that repo.
After the observation window, `corral learnings report` compares normalized
before/after metrics. Regression or expiry is surfaced; corral never silently
removes or rewrites an adopted rule.

### Included

- evidence enrichment and exact answer→permission correlation;
- repo-scoped learning store with provenance and state transitions;
- deterministic repeated-approval miner for exact Bash rules;
- counterfactual historical verifier;
- `corral learnings scan|list|show|adopt|reject|report`;
- authenticated API and dashboard proposal cards;
- adopted-rule injection into corral's per-session pinned settings;
- 14-day baseline/post-adoption measurement, TTL, regression flagging;
- deterministic E2E with fake clock/history plus a real 2-week dogfood gate.

### Excluded from v0.6.0

- automatic adoption, automatic repo writes, and automatic rollback;
- wildcard/generalized Bash rules (an exact approval never proves a broader
  prefix safe);
- non-Bash permission synthesis;
- direct auto-answering through hook output or PTY input;
- any hosted model or external telemetry;
- the remaining RUNBOOK artifact kinds (§15).

## 2. Evidence contract

### 2.1 `permission.requested` enrichment

Keep the existing event kind and extend its JSON payload compatibly:

```json
{
  "prompt_id": "p1",
  "tool_name": "Bash",
  "tool_use_id": "toolu_01",
  "tool_input": {"command":"npm test"},
  "redactions": [],
  "truncated": false
}
```

The state engine uses the unredacted in-memory payload for correlation, as it
does today. For persistence it independently JSON-marshals `tool_input`, runs
`redact.Redact`, then caps the result. Invalid JSON is stored as a redacted JSON
string rather than injected as raw JSON. `redactions` contains rule names only;
never original bytes. `truncated=true` makes the observation ineligible.

The returned event `seq` remains `openReq.hookSeq`. Resolution events add
`request_seq` so no consumer has to reimplement prompt/tool matching:

```json
{"request_seq":41,"outcome":"approved","settle_ms":2870,"prompt_id":"p1","tool_name":"Bash"}
```

### 2.2 Answer correlation

When the current session is blocked and its `BlockedReason.HookSeq` is valid,
HTTP and ntfy answer events add `permission_request_seq`:

```json
{"via":"http","len":3,"permission_request_seq":41}
```

The HTTP path currently omits `via`; M6 adds `via:"http"`. Answers delivered
while not blocked or against a non-permission reason omit the correlation.
This is audit metadata only: answers still never force a state transition.

### 2.3 What counts as a manual approval

For one session and request sequence `R`, in append order:

1. `permission.requested` seq `R`, eligible exact Bash input;
2. `permission.blocked` for the same request;
3. `session.answered.permission_request_seq == R`;
4. `permission.resolved.request_seq == R && outcome == "approved"`.

Any missing step, failed/denied outcome, redaction, truncation, undecodable
input, or answer after resolution excludes it. Multiple answers still count as
one approval. Auto Mode approvals have no correlated answer and never teach.

## 3. Repository identity

Learning scope is the canonical physical repository, not an arbitrary session
subdirectory and not a task worktree.

- For a task session, `tasks.repo` is authoritative.
- Otherwise resolve `git -C <cwd> rev-parse --show-toplevel` through a small
  no-shell helper. Resolve symlinks/absolute-clean the result.
- If the cwd is not a git repository, its absolute-clean cwd is the scope.
- Persist the resolved repo string in each learning/evidence projection; never
  rerun repository discovery while rendering an existing learning.

Historical rows are resolved during scan. If their cwd no longer exists, they
are skipped with a diagnostic count, not incorrectly assigned elsewhere.

## 4. Store model — migration `0006_learnings.sql`

```sql
CREATE TABLE learnings (
  id                 TEXT PRIMARY KEY,
  repo               TEXT NOT NULL,
  kind               TEXT NOT NULL,
  fingerprint        TEXT NOT NULL,
  status             TEXT NOT NULL,
  content_json       TEXT NOT NULL,
  evidence_count     INTEGER NOT NULL,
  baseline_json      TEXT NOT NULL,
  verification_json  TEXT,
  created_ms         INTEGER NOT NULL,
  updated_ms         INTEGER NOT NULL,
  verified_ms        INTEGER,
  proposed_ms        INTEGER,
  adopted_ms         INTEGER,
  rejected_ms        INTEGER,
  expires_ms         INTEGER NOT NULL,
  UNIQUE(repo, kind, fingerprint)
) STRICT;
CREATE INDEX learnings_repo_status ON learnings(repo, status, updated_ms);

CREATE TABLE learning_evidence (
  learning_id TEXT NOT NULL,
  event_seq   INTEGER NOT NULL,
  role        TEXT NOT NULL,
  PRIMARY KEY (learning_id, event_seq, role),
  FOREIGN KEY (learning_id) REFERENCES learnings(id) ON DELETE CASCADE,
  FOREIGN KEY (event_seq) REFERENCES events(seq) ON DELETE RESTRICT
) STRICT;

CREATE TABLE learning_measurements (
  id              TEXT PRIMARY KEY,
  learning_id     TEXT NOT NULL,
  phase           TEXT NOT NULL,
  window_start_ms INTEGER NOT NULL,
  window_end_ms   INTEGER NOT NULL,
  metrics_json    TEXT NOT NULL,
  verdict         TEXT NOT NULL,
  created_ms      INTEGER NOT NULL,
  FOREIGN KEY (learning_id) REFERENCES learnings(id) ON DELETE CASCADE
) STRICT;
CREATE INDEX learning_measurements_learning ON
  learning_measurements(learning_id, created_ms);
```

String enums are validated in Go, following sessions/tasks. `content_json` for
`kind=permission_rule` is:

```json
{"tool":"Bash","command":"npm test","rule":"Bash(npm test)"}
```

`fingerprint = SHA-256(kind + NUL + canonical content_json)`. Repo is excluded
so identical rules in different repos remain independent rows while retaining
the same content identity. Re-scanning is idempotent: it upserts evidence and
counts but never resurrects a rejected learning unless the operator explicitly
requests reconsideration (deferred).

### 4.1 State machine

```text
candidate -> verified -> proposed -> adopted
    |            |          |
    +----------> rejected <-+
                              adopted -> regression_flagged
                              adopted -> stale
regression_flagged|stale -> retired
```

Only `proposed` may be adopted. Reject is terminal in v0.6.0. Retirement is an
explicit operator action; automatic decay flags but does not mutate active
settings. Every transition and failed transition is transactional with its
materialized row; successful transitions append `learning.*` after commit.

## 5. Mining and deterministic synthesis

`internal/learning.Miner` consumes a typed store query, never raw DB access.
Defaults: 14-day lookback, minimum 3 distinct manual approvals, 90-day TTL.
The clock and thresholds are injected.

Eligibility for `permission_rule`:

- exact `ToolName == "Bash"`;
- `tool_input.command` is a non-empty UTF-8 string;
- no redactions/truncation;
- command length <= 1 KiB and contains neither NUL/newline nor Claude's Bash
  compound separators (`&&`, `||`, `;`, `|`, `|&`, `&`);
- the exact command has at least the configured number of correlated manual
  approvals in the same repo/window;
- no `failed_or_denied` resolution exists for the exact command in that window.

The synthesized rule is exact: `Bash(<command>)`. No wildcard is added. `)` in
the command is conservatively ineligible until a verified escaping contract
exists. Evidence stores the request, block, answer, and resolution event seqs.

The miner never calls Claude and never writes settings. Its output is
`candidate` rows plus `learning.mined` events.

## 6. Verification

The v0.6.0 verifier is a deterministic counterfactual replay over immutable
history:

1. validate content/fingerprint and current Claude permission-rule syntax;
2. replay the candidate against every eligible request in the baseline window;
3. require >= `min_approvals` exact matches, all manually approved, zero
   failed/denied matches, and at least one actual `permission.blocked` event;
4. calculate `avoidable_blocks`, approval count, and evidence coverage;
5. generate the exact before/after pinned-settings JSON and verify both decode;
6. store `verification_json`, then transition candidate→verified→proposed.

This is a real counterfactual for an exact permission rule: those exact calls
would have matched an allow rule. It does not claim the whole task would have
succeeded or cost less. The post-adoption measurement is the authority for
that claim.

A gated `CORRAL_E2E_REAL_CLAUDE=1` test confirms one generated exact rule
against a real installed Claude Code version. Fakeclaude covers plumbing in CI.
Failure to verify moves the candidate to `rejected` with a machine reason and
keeps it out of the proposal UI.

## 7. Adoption and effective settings

`settings.BuildSettingsJSON` gains a variant accepting sorted adopted rules.
The original function remains as a compatibility wrapper for no rules.
Generated JSON is deterministic:

```json
{"permissions":{"allow":["Bash(npm test)"]},"hooks":{...}}
```

Before every fresh spawn and resume, the daemon resolves the session's repo,
loads `status=adopted` permission rules, sorts/deduplicates them, and builds the
pinned settings. Existing live children are not hot-patched.

An explicit `adopt` transaction stamps `adopted_ms`, captures a baseline
measurement ending at that instant, and appends `learning.adopted`. It does not
touch a repository. Existing user/project/managed ask or deny rules still win
because Claude Code owns precedence. This is intentional defense in depth;
post-adoption measurement will expose a rule that had no effect.

Reject records a reason category plus optional operator note after redaction.
Neither secrets nor full answer text enter any learning record.

## 8. Measurement, decay, and the real gate

Each report covers an exact 14-day half-open window. Metrics are repo-scoped:

- `blocked_events`, `sessions`, `blocked_per_session` (primary);
- `task_cost_usd`, `terminal_tasks`, `cost_per_terminal_task` (secondary);
- exact-rule `matched_requests` and `matched_blocks` (diagnostic).

Verdicts require at least 5 sessions in each comparison window; cost verdicts
also require at least 3 terminal tasks per window. Otherwise `inconclusive`.
Improvement requires primary blocked/session to decrease and cost/task not to
increase by more than 10%. Regression is the inverse safety condition. Raw
counts and denominators are always printed.

At adoption, baseline = `[adopted_at-14d, adopted_at)`. Post measurement becomes
eligible at `adopted_at+14d` and uses `[adopted_at, adopted_at+14d)`. Repeated
reports are idempotent by `(learning, phase, window)`.

At `expires_ms`, an adopted rule becomes `stale` only after a report/reaper
scan; it remains effective until explicit retire. A regression becomes
`regression_flagged` and likewise remains active pending operator action.
This avoids an unattended daemon changing permission capability silently.

**Release rule:** deterministic tests may backdate fixtures to prove window
math, but they do not satisfy the RUNBOOK exit criterion. `v0.6.0` is tagged
only after a real dogfood report covering the full two-week post-adoption
window is attached to `docs/dogfood/m6.md` and meets the sufficiency rule.

## 9. API, CLI, dashboard, and auth

Versioned endpoints:

```text
POST /v1/learnings/scan
GET  /v1/learnings?repo=&status=
GET  /v1/learnings/{id}
POST /v1/learnings/{id}/adopt
POST /v1/learnings/{id}/reject
POST /v1/learnings/{id}/retire
GET  /v1/learnings/{id}/report
```

Admin and unix-socket callers have full access. Session-scoped TCP tokens may
list/show learnings only for the rooted session's resolved repo; all mutation
routes return 403. Dashboard snapshots include proposal summaries but not all
evidence; detail is fetched on demand.

CLI:

```text
corral learnings scan [--repo PATH]
corral learnings list [--repo PATH] [--status proposed]
corral learnings show <id> [--diff]
corral learnings adopt <id>
corral learnings reject <id> [--reason TEXT]
corral learnings retire <id>
corral learnings report <id>
```

Human output names the scope, evidence count, exact rule, status, expiry, and
measurement denominators. `--json` returns stable typed shapes. Adoption and
retirement require an explicit subcommand/click; there is no bulk implicit
confirmation.

## 10. Configuration

New independent `[learn]` pipeline: defaults → user config → env. It never
reads repo `.corral.toml`.

```toml
[learn]
window = "336h"             # 14d
min_approvals = 3
ttl = "2160h"               # 90d
min_sessions = 5
min_terminal_tasks = 3
cost_regression_tolerance = 0.10
```

Environment keys use the existing exact mapping convention:
`CORRAL_LEARN_WINDOW`, `CORRAL_LEARN_MIN_APPROVALS`, `CORRAL_LEARN_TTL`,
`CORRAL_LEARN_MIN_SESSIONS`, `CORRAL_LEARN_MIN_TERMINAL_TASKS`, and
`CORRAL_LEARN_COST_REGRESSION_TOLERANCE`.

All fields are user/env-only and explicitly rejected if present in repo config.
There is no `learn.enabled`: scans are explicit in v0.6.0, so merely upgrading
the daemon never starts new background work.

## 11. Events

Add immutable kinds:

```text
learning.mined
learning.verified
learning.proposed
learning.adopted
learning.rejected
learning.measured
learning.regression_flagged
learning.stale
learning.retired
```

They are daemon-scoped because a learning spans sessions. Payloads contain
`learning_id`, `repo`, `kind`, and transition-specific non-secret metrics.
SSE treats them as ordinary invalidations. They never carry answer text or
unredacted tool input.

## 12. Test strategy

- Evidence tests prove secret redaction/truncation, request-seq correlation,
  Auto Mode exclusion, multiple-open-request correctness, and HTTP/ntfy parity.
- Migration/store tests cover schema 0006, enum/state-machine validation,
  idempotent upsert/evidence, transactions, and FK behavior.
- Miner table tests cover threshold/window/repo grouping, every ineligibility
  rule, duplicates, rejection non-resurrection, and fake-clock boundaries.
- Verifier tests prove counterfactual counts, exact JSON diff, no proposal on
  negative evidence, and no filesystem writes.
- Settings tests retain the existing byte golden for no rules and add a sorted,
  deduplicated permissions golden.
- API/scope tests cover admin/unix access, scoped read confinement, mutation
  403s, error envelopes, and token filtering.
- CLI tests cover every command in human and JSON modes.
- Measurement tests backdate two full windows with injected clock and assert
  improvement/regression/inconclusive/TTL boundaries.
- Dashboard tests cover proposal render, evidence detail, explicit adopt/reject,
  SSE refetch, and no token leakage.
- E2E always runs with fakeclaude: repeated manual approvals → scan → proposal
  → adopt → a new session receives the pinned rule → synthetic post window →
  improved report; assert the repo tree is byte-identical before/after.
- Gated real-Claude rule verification uses `CORRAL_E2E_REAL_CLAUDE=1`.
- Full close: `go build ./...`, `go vet ./...`, `go test -race ./...`.

## 14. Security review checklist

- No candidate/adopt/report path writes beneath a repo path.
- No persisted event/learning includes plaintext answers or unredacted input.
- Repo files cannot configure learning thresholds or adoption.
- A candidate cannot affect settings before explicit adoption.
- Session-scoped tokens cannot mutate learnings.
- Existing ask/deny/managed Claude rules retain precedence.
- Exact rules are never generalized with wildcards.
- Regression/expiry never silently widens or narrows permissions.
- Real-Claude verification is opt-in and uses temp/fake HOME/state.
- No merge, push, or user-repo mutation is introduced.

## 15. Deferred after v0.6.0

- **Operational memory** — distilled setup commands/flakes/quirks injected at
  SessionStart after structured-model synthesis and sandbox verification.
- **Model-routing bandit** — task-type/model outcome policy feeding M4 task
  defaults; needs larger outcome samples and quota signals.
- **Skill synthesis** — draft `SKILL.md` artifacts with sandbox verification;
  adoption may write a repo file only after explicit diff approval.
- **Failure regression corpus** — capture and replay failed tasks via
  `corral regress`.
- **General structured synthesizer** — cheap-model interface with schema,
  budget, timeout, prompt-version provenance, and no network by default.
- **Automatic scheduled scans** — explicit scans first; add a daemon scheduler
  only after runtime cost and noise are measured.
- **Automatic adoption/rollback** — intentionally not planned; permission
  capability changes remain human actions.
