# corral M3 design — checkpoint/resume + idle reaping

**Milestone goal (RUNBOOK.md:146-154):** sessions survive daemon restarts and
machine reboots; long-idle sessions are checkpointed and reaped to free
resources, then woken on demand; checkpoints happen at *turn boundaries* so a
resume never lands mid-turn. **Exit criteria:** chaos tests (§5 of RUNBOOK)
green; a machine reboot loses nothing but in-flight turns.

This doc builds on what M1/M2 already shipped. Most of "crash recovery" already
exists — the honest scope of M3 is *idle reaping*, *wake-on-demand*, and
*making `TurnBoundaryVerified` mean something*. We say so plainly and resist
re-building what works.

---

## 0. What already exists (do not rebuild)

Grounding the design in the real tree (verified via source read, not memory):

- **Recovery** — `internal/supervisor/recover.go`. On daemon start, `Recover`
  iterates `sessions` where `desired_state='running'`. For each: if the old
  process is still `Alive(pid, proc_start_ns)` it is **reaped, not re-adopted**
  (the daemon lost the PTY fd across the restart — `reapOrphan` SIGTERM/grace/
  SIGKILL), then relaunched via `--resume <claude_session_id>`. Emits
  `session.orphan_reaped` then `session.resumed` / `session.unresumable`.
  Sessions with `desired_state='stopped'` are **skipped**. This is correct and
  M3 leaves the predicate untouched.
- **Checkpoint** — `internal/checkpoint/resume.go`. `ResumeCheckpointer.Checkpoint`
  today: sets `status=stopping`, SIGTERM to PGID, waits grace, unconditional
  SIGKILL, persists `claude_session_id=s.SessionID`, `status=exited`,
  `exit_signal`, `ended_at_ms`, returns `Token{TurnBoundaryVerified:false}`.
  **It never inspects the transcript** — the `false` is a placeholder from M1.
- **Resume args** — `BuildArgv` (`spawn.go:47`) already emits
  `--resume <ResumeFrom>` when a spec carries `ResumeFrom`, else `--session-id`.
- **`Resumable`** — `resume.go:166`: true iff the row has a `claude_session_id`
  **and** the on-disk transcript exists. Independent of `desired_state`. This is
  the correct wake predicate (see §3).
- **Stale (M2)** — `engine_real.go:200`, `state.stale_after` default 15m. A
  **render-time** flag only. Never kills anything. M3's reaper is a separate,
  action-taking mechanism; we do not overload Stale.

**Absent — M3 adds:** idle reaper (no stub exists), `corral wake`, activity
tracking (`last_activity_ms` column), truthful turn-boundary detection.

## 2. Activity tracking (step 12)

### 2.1 What counts as activity

**Activity = human / external input.** Precisely: `WriteInput` (a human or an
answer typed into the PTY), a client attach, and an inbound hook event. Agent
PTY **output does not count** — a session streaming output for an hour with no
human present is *exactly* what we want to reap. Agent output is *liveness*, not
*activity*; conflating them would make the reaper never fire on a runaway
session. This is written into the migration comment so it is not "fixed" later.

### 2.2 Migration 0003

```sql
-- 0003_activity.sql
-- last_activity_ms: unix-ms of the last HUMAN/EXTERNAL input to this session
-- (WriteInput, attach, inbound hook). NOT bumped by agent PTY output — an
-- idle-from-the-human's-view session is the reap target even while the agent
-- streams. Seeded to started_at_ms for existing rows.
ALTER TABLE sessions ADD COLUMN last_activity_ms INTEGER NOT NULL DEFAULT 0;
UPDATE sessions SET last_activity_ms = COALESCE(started_at_ms, created_at_ms, 0);
```

`store.TouchActivity(ctx, id, ms)` — single-column UPDATE, called from:
- `Registry.WriteInput` (supervisor.go:525) after a successful write,
- attach handler on attach,
- hook ingest path (`hook.received`).

Bumping is best-effort (a failed touch logs and moves on; it must never fail an
input write).

### 2.3 Config

```toml
[session]
idle_timeout = "0s"   # 0 = disabled (default). e.g. "30m" to enable reaping.
```

`config.State.IdleTimeout time.Duration`, default `0`. **Default off is a
deliberate safety choice** — shipping a tool that kills the user's sessions by
default is how a tool gets uninstalled. `[state]`/`[session]` remain
user-file/env only per the repo trust boundary (`repo_allowlist.go`) — a cloned
repo cannot set `idle_timeout`.

## 3. Idle reaper (step 13)

### 3.1 The reap set — narrow on purpose

A live session is reaped iff **all** hold:

1. `idle_timeout > 0` (feature enabled), and
2. `agent_state == idle`, and
3. **not attached** (`LiveSession.Attachment == nil`), and
4. `now - last_activity_ms > idle_timeout`.

Condition (2) is load-bearing twice over:

- **Correctness of the checkpoint.** `agent_state==idle` *is* a turn boundary —
  the agent has finished its turn and is waiting. Checkpointing here can never
  lose an in-flight turn, so the reaper never triggers the lossy path. This is
  why M3 can ship truthful checkpoints without stream-json (§5).
- **We deliberately do NOT reap `working` or `blocked`.** `working` = the agent
  is busy; killing it loses the turn. `blocked` = waiting for a permission
  answer; killing it loses the pending prompt (and whether `--resume` restores a
  mid-flight permission prompt is an open spike question). Reaping a
  long-blocked session is a **future** refinement — noted, not built. M2's
  notify path already handles the "nobody's answering" case.

### 3.2 What reaping does — and the `desired_state` decision

Reap = `checkpointer.Checkpoint(ctx, ls, "idle_reap")` **then set
`desired_state='stopped'`**, then emit `session.idle_reaped`.

> **Why `stopped`, not `running`.** This is the design's sharpest edge and got
> it wrong in the first draft. `recover.go:32` relaunches *every*
> `desired_state='running'` row on daemon start. If idle-reap left
> `desired_state='running'`, then: reap 20 sessions overnight → restart the
> daemon → 20 claude processes spring back to life. The daemon would fight the
> reaper. So idle-reap sets `desired_state='stopped'`; recovery skips it; it
> stays checkpointed until explicitly woken.

This forces a clean separation of two properties that a single boolean was
conflating:

| property | means | encoded by |
|---|---|---|
| **resumable** | can be brought back (`claude_session_id` + transcript on disk) | `Resumable()` — already exists, already `desired_state`-independent |
| **should be running now** | daemon should have a live process | `desired_state` |

An idle-reaped session is **resumable** but should **not** be running. `corral
wake` keys off `Resumable()`, never off `desired_state`.

**Do we need to distinguish "idle-reaped" from "user-killed" in the store?**
No. Wake behaves identically for both (both are resumable rows the user asked to
bring back). The distinction that matters for humans — "this stopped because it
was idle" vs "I killed it" — is carried by the `session.idle_reaped` vs
`session.killed` **events**, not by a lifecycle column. So migration 0003 adds
`last_activity_ms` only; no reason column.

### 3.3 The loop

A single daemon-owned goroutine (`reaper.Run(ctx)`), started in daemon startup
after recovery, stopped in shutdown before the store closes. Tick interval =
`min(idle_timeout/4, 1m)`, floor 5s. Each tick: `registry.ListLive()`, filter by
§3.1, checkpoint the survivors sequentially (reuse the shutdown grace; a reap
storm is rare and sequential keeps SIGKILL pressure sane). Ctx cancellation ends
the loop promptly.

New event kind: `session.idle_reaped` (payload: idle duration observed).

## 4. Wake (step 14)

### 4.1 `corral wake <session>`

`supervisor.Wake(ctx, name)`:
1. Look up the row by name. Error if not found.
2. If already live → no-op success ("already running").
3. If `!Resumable(row)` → error `session unresumable: <reason>` (no
   `claude_session_id`, or transcript gone).
4. Else: `checkpoint.Restore(row)` → `Spec{ResumeFrom: claude_session_id, …}`,
   `registry.Spawn(spec)`, set `desired_state='running'`, emit
   `session.resumed` (reason `"wake"`).

Steps 3–4 are exactly what `recover.go:recoverOne` already does for the resume
branch. **Extract that into `resumeOne(ctx, row, reason)`** and call it from both
recovery and wake — one resume path, one place for bugs to live.

### 4.2 Auto-wake on answer — HTTP path only, ntfy untouched

When `corral answer` (HTTP `POST /v1/sessions/{name}/answer`) targets a
**resumable-but-not-live** session, wake it first, wait for it to reach live,
then deliver the answer. This makes "phone buzzes hours later, you answer, the
session comes back and continues" work for the HTTP path.

**The ntfy reply subscriber is explicitly NOT touched in M3.** Its gate 3
(`reply.go`) rejects unless the session is **live and blocked**; a
woken-from-checkpoint session is neither at the instant the ntfy message
arrives. Making auto-wake work over ntfy means amending a security gate we just
shipped and verified live — that deserves its own advisor pass, not a drive-by
in M3. M3 keeps the ntfy path byte-for-byte as shipped; auto-wake is
HTTP-answer-only. **Tracked as an M4 item.**

## 5. Truthful turn-boundary checkpoint (step 15)

### 5.1 Make `TurnBoundaryVerified` mean something

Today `Checkpoint` returns `TurnBoundaryVerified:false` unconditionally.
`turnboundary.go` adds `LastRecordIsCompletedTurn(transcriptPath) (bool, error)`:
tail-read the session `.jsonl`, find the last record, return true iff it is a
completed assistant turn (not a mid-tool-loop / partial record). `Checkpoint`
calls it just before SIGTERM and stamps the real value into the `Token` and the
row.

For the **reaper** path this is always `true` by construction (§3.1 cond 2 —
the agent is idle). For the **shutdown** path of a `working` session it may be
`false`, and that is recorded honestly.

### 5.2 What we deliberately do NOT do in M3: re-send

The spike finding ("session `.jsonl` isn't flushed incrementally; a SIGKILL
mid-turn loses the in-flight turn; recovery should re-send the last prompt")
motivated a re-send mechanism. **M3 does not build it, on purpose:**

- For an **interactive PTY session there is no captured record of the last
  prompt.** The user typed it into a TUI. We have `Screen` (grid state, not
  input history) and `output.log` (capped, `O_TRUNC` on each spawn,
  diagnostics-only per `outputlog.go`). Nothing durable holds user input. There
  is nothing to re-send.
- The finding is really about `-p` / **stream-json headless** sessions, where a
  structured prompt record exists — that is **M4**.
- The reaper never loses an in-flight turn (§3.1). The only lossy path is
  shutdown-checkpoint of a `working` session, and RUNBOOK's own exit criterion
  is "a reboot loses nothing **but in-flight turns**." Recording
  `TurnBoundaryVerified=false` + emitting an event + accepting the loss is
  therefore *within* the milestone, not a gap.

So M3 step 15 = **detect and record turn-boundary state honestly.** Re-send is
deferred to M4 and this deferral is written down here so it is not silently lost.

## 6. Chaos tests (step 16)

Mapped to RUNBOOK §5:

1. **Idle reap round-trip** — spawn (fake CLI), drive to `idle`, advance a fake
   clock past `idle_timeout`, tick reaper → assert `status=exited`,
   `desired_state=stopped`, `session.idle_reaped` emitted, `Resumable()` true.
2. **Wake round-trip** — from the reaped state, `Wake` → assert live,
   `desired_state=running`, `--resume` in argv, `session.resumed(reason=wake)`.
3. **Attached session immune** — attached + idle + past timeout → reaper does
   **not** touch it.
4. **Working/blocked immune** — same, for `agent_state ∈ {working, blocked}`.
5. **Daemon restart after reap** — reaped (`desired_state=stopped`) row is
   **not** resurrected by recovery (guards against the first-draft bug).
6. **Restart of a running session** — unchanged M1 behavior still green
   (orphan_reaped → resumed).
7. **Auto-wake on HTTP answer** — answer to a reaped session wakes + delivers.

Fake clock + fake CLI (already used in supervisor/checkpoint tests) keep these
deterministic and `-race`-clean.
